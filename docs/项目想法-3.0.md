# OpenVow 设计 3.0（最终版）

> 📄 **本文已合并进《[OpenVow 设计文档集](design/README.md)》，保留作工作稿。** 对外交付与后续维护以设计文档为准。
>
> **这是唯一真源。** 1.0、2.0、2.1 归档为历史，不再维护；本文与它们冲突时，以本文为准。
>
> 3.0 相对 2.1 的实质变化：接口前置为独占任务、测试由独立任务产出并用"红测试"验收、集成变成任务（不再是一个阶段）、任务类型学成型、校验只剩四层、代码同步与 canonical repo 补全、安全与成本模型补全。

---

## 0. 一页速览

**一句话**：OpenVow 是一个私有工程的任务中台——人定契约，终端干活，平台只做派发、校验、归集、合并。

**四条不可让渡的边界**

| 边界 | 含义 |
| --- | --- |
| 不持有模型凭证 | 平台没有任何 API Key / 订阅账号，风控与成本全在终端 |
| 不主动调用 | 平台永不向模型发请求，只回应终端 |
| 不改写产物内容 | 平台只做校验、归档、按序合并，不做修补 |
| 不内置拆解 | 拆解也是一个任务，由 planner 终端完成 |

**一条原则**：

> **平台里没有隐含动作，只有任务。**
> 凡是"产出或改变内容"的事——拆解、写接口、写测试、写实现、合并、修复——都是任务，都走同一套 claim / 校验 / submit。协议只负责搬运。

**主链路**

```
人 ──需求(items)──► decompose ──► planner 终端 ──► graph 草案
                                                │
                          人审 approve ◄── V1–V8 校验
                                │
                                ▼
 interface ──► test ──► implement ──► integration ──► merged
  (骨架)      (红)      (绿)          (全量)
                 ▲                       │
                 └──────── repair ◄──────┘  集成失败时
```

**三句话**
1. 契约在动手之前就冻结，产物不需要二次加工。
2. 验收由独立任务产出、平台冻结执行，实现方无法给自己判卷。
3. 合并是一次真实的执行，失败会生成修复任务，而不是一句"集成失败"。

## 1. 定位

### 1.1 它是什么

把一个较大的软件需求，切成**文件不相交、接口已冻结、验收可执行**的子任务，分发给多个自带模型账号的终端并行执行，并把合格的产物按 DAG 顺序合并成可编译的主干。

### 1.2 它不是什么（scope guard）

这一节比"它能做什么"更重要，请先读这里：

| 不适合 | 原因 |
| --- | --- |
| 单文件小改动 | 建契约的成本远大于改代码本身 |
| 强耦合的存量代码改造 | 热文件会把并行度压到 1（见 §7.5） |
| 需要架构判断的工作 | 平台明确不做设计决策，`decisions[]` 必须有人给 |
| 替代 code review | 平台只保证"结构合法 + 验收通过"，不保证"设计正确" |
| 一个人一个账号的场景 | 分布式的全部机制都是净开销（见 §2.2） |
| 需要长期演进的项目治理 | 它只管一次需求到合并，不管版本规划、发布、回滚策略 |

### 1.3 差异化的正确表述

不要再说"市面上没有产品这样做"——可证伪，且容易被一句"A2A 不就是这个吗"问死。

站得住的表述是**三元组合**：

> **私有工程 + 代码级契约 + 终端主动拉取**，这三件事目前没有产品同时做全。单点都不新，组合是新的。

另外明确弃用一条旧主张："无内置 Agent 是差异化"——Airflow、Prefect 也没有内置 Agent，这不是差异。

## 2. 成立条件与指标

### 2.1 三个前提（缺一个就会空转）

1. **有 ≥3 个可独立干活的执行体**（人 / 账号 / 机器）。只有一个，分布式毫无意义。
2. **工作以新增文件、新增模块为主**。改造存量时，注册表、路由、清单这类热文件会把 DAG 串行化。
3. **接受"平台只保证结构与验收，不保证内容质量"**，并且有评审带宽兜底。

### 2.2 回本门槛（经验值）

| 指标 | 低于此值不建议上 | 说明 |
| --- | --- | --- |
| 独立执行体 | 3 个 | 2 个只能做"左右互搏"，收益 < 协调成本 |
| 每周子任务数 | 15 | 低于此值，人工拆解 + 串行更快 |
| 单任务平均规模 | 100–400 行 | 太小则契约成本占比过高，太大则失败代价过高 |

### 2.3 成功指标（north star 与护栏）

| 指标 | 定义 | 目标方向 |
| --- | --- | --- |
| **墙钟时间** | 需求发布 → merged | 主指标，越短越好 |
| 一次通过率 | accepted / submitted | ≥ 70% |
| 集成失败率 | integration failed / 总集成次数 | ≤ 15% |
| 人工评审负荷 | 分钟 / accepted 任务 | ≤ 10 分钟 |
| 单元返工率 | 被 repair 牵连的任务占比 | ≤ 10% |
| 每 accepted 任务成本 | token + 复跑 + 人工折算 | 需要可观测，不设硬指标 |

**并行会放大评审负荷**：如果评审速度是 ×1，而产出变成 ×5，积压就是 ×5。所以"人工评审负荷"必须和"墙钟时间"并列成为设计指标，否则这套系统只是在生产评审债务。

### 2.4 风控叙事降级

"规避封号"是**订阅账号自动化**的套利，不是护城河：

- 走官方 API 不封号，只是花钱；
- 平台化之后，这套叙事在商业计划书里很难解释；
- 政策一变，卖点消失。

保留它，但降级为**附带好处**。真正的价值排序是：**并行缩短墙钟 > 前置契约减少返工 > 产物可审计**。

## 3. 架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 控制面（人）                                                  │
│  需求条目化 · 图审批 · 契约修改 · 看板                          │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 调度面（平台，无模型、无 Agent、无模型 Key）                    │
│  claim(原子+写集互斥) · 租约/心跳/检查点 · DAG 解锁             │
│  V1–V8 图校验 · L0–L3 产物校验 · 信任分抽检 · 准入 · 审计       │
└──────┬───────────────────────────────────────┬───────────────┘
       │ 产物（内容寻址）                        │ 任务 / 代码
┌──────▼──────────────┐                ┌───────▼───────────────┐
│ 产物库 Artifact     │                │ canonical repo 镜像   │
│ sha256 · 只读 · 不可变│                │ 平台维护的唯一主干     │
└─────────────────────┘                └───────┬───────────────┘
                                               │
┌──────────────────────────────────────────────▼───────────────┐
│ 执行面（平台边界之外）                                        │
│ Claude Code · DeepSeek Harness · 自研 Agent · planner         │
│ 各自账号、各自风控、各自限速；通过 MCP 适配器接入              │
└──────────────────────────────────────────────────────────────┘
```

相对 2.x 的两处结构变化：

1. **产物库旁边多了一个 canonical repo**。没有它，终端看不到别人已 `accepted` 的成果，并行无从谈起（§3.4）。
2. **集成不再是一个阶段，而是执行面上的一个任务**，因此执行面包含了"合并"这件事。

### 3.2 四类参与者

| 参与者 | 职责 | 持有凭证 |
| --- | --- | --- |
| 人 | 写需求条目、批准图、改契约、处理 `needs_human` | human token |
| planner 终端 | 把需求拆成图 | terminal token（scope: planner） |
| 执行终端 | 领 `interface` / `test` / `implement` / `integration` / `repair` | terminal token |
| 平台 | 派发、校验、归集、合并、审计 | 无模型凭证 |

### 3.3 一次完整循环（12 步）

1. 人把需求写成**条目化文档**（每条有稳定 id，如 `R-14/2.3`，后续 `covers` 引用它）。
2. 人发一个 `decompose` 任务（`kind: decompose`，写集为空）。
3. planner 终端 claim，读需求 + 仓库快照 + `decisions[]`，产出 `task_graph.json` 草案。
4. 平台跑 **V1–V8**，把 `violations[]` 连同图一起返回给 planner；不过就改，改完再交。
5. 人审 `diff`（只看改动节点），可局部改、可驳回；通过后图 `active`。
6. 平台把图展开成任务，按 `kind` 排拓扑：`interface` 全在前，`test` 次之，`implement` 最后，`integration` 由平台自动生成、置于末尾。
7. 各终端独立 claim。**同时被认领的任务，写集两两不相交**（§7.2 的 SQL 保证）。
8. 每个终端提交产物 + 证据；平台跑 **L0–L3**，通过则 `accepted`，解锁下游。
9. 一个 merge group 的成员全部 `accepted` 后，`integration` 任务解锁。
10. 某终端 claim `integration`，把产物按 DAG 顺序应用到一个临时分支，在容器里全量构建 + 全量测试。
11. 通过 → 合并到 canonical 主干，`merged`；失败 → 平台自动生成 `repair` 任务（带失败包），回到第 7 步。
12. 全部 `merged` 后需求闭环；看板记录墙钟、成本、返工。

### 3.4 代码同步与 canonical repo（2.x 缺失的一环）

终端必须能看到别人已 `accepted` 的代码，否则每个任务都在对着一份过期快照工作。

| 项 | 设计 |
| --- | --- |
| 镜像 | 平台维护 `repos(mirror_url, canonical_branch, head_commit)`，从 origin 单向拉取 |
| 认领 | `claim` 返回 `repo_url` 与 `base_commit`；终端自行 `git fetch` 后 checkout |
| 提交 | 终端**不 push**。只交文件哈希，二进制走 artifact 上传 |
| 合并 | 只有 `integration` 任务能把产物写成 commit（平台代写，不改内容） |
| 回传 origin | 可选，按项目配置；默认只留在平台主干 |

这样"平台不改写产物"与"平台要维护主干"就不矛盾了：**平台只决定顺序，不修改任何字节。**

## 4. 任务类型学（3.0 的核心）

### 4.1 五种类型

| kind | 目的 | writes | acceptance | 依赖 | 产物 |
| --- | --- | --- | --- | --- | --- |
| `decompose` | 需求 → 图 | ∅ | `graph_valid` | 无 | `task_graph.json` |
| `interface` | 冻结接口骨架 | 接口文件（独占） | `skeleton_build` | decompose 批准 | 骨架源码 + 签名清单 |
| `test` | 产出验收测试 | 测试文件 + fixtures | `red_tests` | interface accepted | 测试源码 + 期望失败证据 |
| `implement` | 实现功能 | 实现文件（不含接口/测试） | `green_tests` | test accepted | 实现源码 |
| `integration` | 合并 + 全量验证 | 全仓（受控） | `full` | 组内全部 accepted | 合并 commit + 集成报告 |
| `repair` | 修集成失败 | 冲突相关文件 | `full` | integration failed | 修复 diff |

六行是因为 `repair` 是 `integration` 的变体（同一套验收，不同的输入和写集），但在调度、权限、重试策略上需要区别对待，所以单列。

### 4.2 `interface`：接口前置，独占，只读

**要解决的问题**：两个并行任务各自发明一套 API，各自用 stub 测过，合并时对不上。

**做法**：

- 图中每个模块至少有一个 `interface` 任务，产出**可编译的骨架**：
  - Rust：`pub fn parse(s: &str) -> Expr { todo!() }`
  - TypeScript：`export function parse(s: string): Expr { throw new Error("not implemented") }`
  - Python：`def parse(s: str) -> Expr: raise NotImplementedError`
  - 以及 `.proto` / `.d.ts` / `trait` / `interface` 定义。
- 骨架必须是**能编译通过**的，否则下游测试写不出来。
- 该任务的 `writes` 即接口文件集合；`accepted` 之后，这些路径在**整张图内变为只读**：
  - 任何后续任务的 `writes` 命中它们 → V2 直接拒绝；
  - 提交时命中 → L0 拒绝；
  - 想改 → 只能走图修订（新 `interface` 版本），并把下游标记 `stale`。
- 同时产出 `openvow.interface.json` 签名清单（由各语言的提取器生成，不让模型手写）：

```json
{
  "module": "parser",
  "symbols": [
    { "path": "parser::parse", "signature": "fn(&str) -> Expr", "file": "src/parser/mod.rs" },
    { "path": "parser::Expr",  "signature": "enum", "file": "src/parser/ast.rs" }
  ]
}
```

**验收**：`skeleton_build` —— 只要求构建通过，不跑逻辑测试（骨架里全是 `todo!()`，跑了必然 panic）。

**为什么必须先做**：它把"接口长什么样"从**隐式约定**变成**显式产物**。没有它，`decisions[]` 只能覆盖人想到的部分，剩下的分歧会全部堆到集成阶段爆炸。

### 4.3 `test`：独立任务，用"红测试"验收

**要解决的问题**：如果实现方自己写测试，它只要把断言改软就能通关（2.1 的洞）。

**做法**：

- 测试由**独立任务**产出，`depends_on` 指向 `interface`，`writes` 只含测试与 fixtures；
- 实现任务的 `depends_on` 指向测试任务，且**测试文件不在实现的写集里**；
- 平台在复跑实现任务时，**用冻结的测试覆盖终端交上来的测试**（见 §5.3），改了也无效。

**验收（这是最巧妙的一处）**：`red_tests` —— 测试在**骨架上必须失败**。

```json
"acceptance": {
  "kind": "red_tests",
  "build": "cargo test --locked --no-run",
  "run": "cargo test --locked",
  "expect": "fail",
  "min_failing_ratio": 0.8,
  "timeout_s": 900
}
```

判定条件（全部满足才算 accepted）：

1. `build` 退出码为 0 —— 测试能编译；
2. `run` 退出码非 0 —— 确实有失败；
3. 输出里有 `test result: FAILED`，且失败用例数 / 总数 ≥ 0.8 —— 不是"只有一个用例红、其余全绿"的假红；
4. 失败原因是断言或 `not implemented` panic，不是编译错误。

**为什么它能防住空测试**：一句 `assert!(true)` 在骨架上是**通过**的，于是 2 不成立、整单被拒。想让测试被接受，唯一的办法是写出"针对未实现行为会失败"的断言。

**为什么它不完美**（要诚实）：它防的是"空洞测试"，防不住"测试写错了需求"。后者只能靠 V4 覆盖度 + 人工抽检。

### 4.4 `implement`

- `writes` = 实现文件；接口文件与测试文件**不在其中**；
- `depends_on` = 对应 `test`（以及同模块 `interface`）；
- 验收 `green_tests`：冻结测试全绿 + lint 零 error；
- 提交时若包含测试文件 → L1 直接拒绝（`frozen_file_modified`）。

### 4.5 `integration`：合并本身就是一次执行

**要解决的问题**：2.x 里 L4 是一个"阶段"，失败了没有工作载体，流程停摆。

**做法**：把集成定义成一个任务。

- **谁创建**：平台自动生成，不是 planner 写进图里。规则：一个 merge group（默认 = 整张图；大图可按模块拆多个 group，见 §15）成员全部 `accepted` 后，物化一个 `integration` 任务。
- **写集**：group 内所有节点的写集并集 + 热文件（注册表、清单）。其它任务此时都已 `accepted`，不存在冲突。
- **并发**：全局串行（同一 canonical 分支同一时刻只允许一个 integration 任务），用 SQL 里的 `NOT EXISTS` 约束保证。
- **执行**：claim 的终端拿到 `bundle`（group 内全部产物 + 顺序），在临时分支上按 DAG 顺序逐个 apply，得到 `candidate_commit`，然后在容器里跑全量构建 + 全量测试。
- **通过**：平台把 `candidate_commit` 推到 canonical 主干（fast-forward），组内任务标 `merged`。
- **失败**：产出**失败包**，创建 `repair` 任务（§4.6）。

**验收**：`full` —— 全量构建 + 全量测试，`timeout_s` 给到 3600。

**为什么它必须由终端跑而不是平台跑**：合并可能需要解决语义冲突（两个任务都对，但组合起来类型不匹配），这不是机械操作。平台只负责"按顺序应用 + 跑测试"，判断和修复留给终端。

### 4.6 `repair`

- 由 integration 失败触发，输入是失败包：`candidate_commit`、失败测试名、日志片段、涉及的 diff。
- `writes`：默认 = 失败测试覆盖到的文件；无法定位时放开到整个 group。
- **终端选择**：优先分给**没有参与产出这些文件**的终端（避免"作者盲区"），无可用终端时回退。
- `accepted` 后，integration 以新 attempt 重跑。
- `integration` 最多 3 次；超过 → `needs_human`，图级告警。

### 4.7 `decompose`

- 输入：需求条目、`base_commit`、`decisions[]`、历史图的正/负样本；
- 输出：`task_graph.json`（只输出这个，不要解释文字）；
- 验收 `graph_valid`：V1–V8 全过；
- 图不占任务池，未批准前执行终端看不见。

### 4.8 类型拓扑约束（V8 检查）

```
decompose → interface → test → implement → integration → merged
                                  ▲            │
                                  └─ repair ◄──┘
```

硬规则：
- 任何 `implement` 的祖先链上必须有 `interface` 与 `test`；
- `test` 的 `depends_on` 必须指向 `interface`；
- `integration` 不进图（平台生成），图里出现即报错；
- 同一模块必须有且只有一个 `interface`（避免两套并存）。

## 5. 契约体系

### 5.1 任务契约字段

```json
{
  "id": "N-03",
  "kind": "implement",
  "title": "解析器主流程",
  "summary": "基于 N-01 的骨架实现 parse / parse_expr",
  "writes": ["src/parser/impl/**"],
  "reads": ["src/parser/mod.rs", "src/parser/ast.rs", "tests/parser/**"],
  "provides": [],
  "consumes": ["parser::parse", "parser::Expr"],
  "depends_on": ["N-01", "N-02"],
  "covers": ["R-14/2.1", "R-14/2.2"],
  "acceptance": {
    "kind": "green_tests",
    "build": "cargo build --locked",
    "run": "cargo test --locked parser",
    "expect": "pass",
    "timeout_s": 900
  },
  "est": { "files": 3, "diff_lines": 320 }
}
```

字段约束：

| 字段 | 规则 |
| --- | --- |
| `writes` | 相对仓库根的 glob；两条任务相交 → 拒；命中 interface 冻结路径 → 拒 |
| `reads` | 只影响终端取上下文，不参与冲突判定 |
| `provides` / `consumes` | 见 §5.2 |
| `depends_on` | 只表达"必须等它 accepted"，不表达"读到它的内容"（后者由 base_commit 保证） |
| `covers` | 必须引用需求条目 id；未覆盖的条目会被 V4 点名 |
| `acceptance.kind` | 枚举：`graph_valid` / `skeleton_build` / `red_tests` / `green_tests` / `full` |

### 5.2 接口契约：provides / consumes 与 V7

- `provides`：本任务新增或承诺的符号（来自 `openvow.interface.json`）。
- `consumes`：本任务调用/依赖的符号。
- **V7 校验闭合性**：每个 `consumes` 必须在同图某个节点的 `provides` 里，或存在于 `base_commit` 的导出符号中。

**诚实说明**：V7 只做**名字级**匹配（符号存在 + 参数个数），不做完整类型检查。真正的类型一致性由 `green_tests` 的编译阶段兜底——这正是为什么测试必须独立且先写：测试编译失败会尽早暴露签名不一致，而不是等到集成。

### 5.3 验收冻结（防作弊的核心机制）

三个冻结点：

| 冻结对象 | 何时冻结 | 怎么强制 |
| --- | --- | --- |
| 接口文件 | `interface` accepted 时 | 写入后全图只读；提交命中即 L0 拒绝 |
| 测试文件 | `test` accepted 时（记 sha256） | 复跑时用冻结版本覆盖提交版本；提交版本若不同 → `frozen_file_modified` |
| 验收命令 | 图批准时 | 任务不能改自己的 `acceptance`；改了就是新版本任务 |

由此得到一条推论：**实现方永远无法给自己判卷。** 它能改的只有实现文件，而判卷的是别人写的、被平台冻结的测试。

### 5.4 图契约 `task_graph.json`

```json
{
  "schema": "openvow/graph/v2",
  "requirement": {
    "id": "R-14",
    "title": "表达式解析器",
    "items": [
      { "id": "R-14/2.1", "text": "支持四则运算与括号" },
      { "id": "R-14/2.2", "text": "错误输入返回带位置的 ParseError" }
    ],
    "base_commit": "9c1f3ab"
  },
  "decisions": [
    { "id": "D-1", "text": "手写递归下降，不引入生成器", "affects": ["N-01"] }
  ],
  "nodes": ["…见 §5.1…"],
  "uncertain": ["需求未说明错误恢复策略"]
}
```

设计取舍：

- **不存 `edges`**：依赖只写在 `depends_on`，边由它推导，避免两处不一致。
- **`decisions[]` 是人的领地**：planner 不得新增架构决策（V8 检查 `decisions` 未变）。
- **`uncertain[]` 是逃生口**：让 planner 承认不确定，比逼它编一个完整图好；不确定项在人审界面置顶。

### 5.5 一个最小但完整的图（三节点）

```
N-01 interface  writes:[src/parser/**]            depends:[]
N-02 test       writes:[tests/parser/**]          depends:[N-01]
N-03 implement  writes:[src/parser/impl/**]       depends:[N-02]
```
平台自动补 `N-04 integration`。三个任务可以两两并行吗？不能——这是 TDD 链，天然串行。**并行发生在多条这样的链之间**，每条链是一个模块。这正是"新增模块为主"场景的形态。

## 6. 校验

只剩两组：**V 组看图，L 组看产物**。合并是任务，不是校验阶段。

### 6.1 V 组（图级，纯函数，不调模型）

| 码 | 检查 | 典型 hint |
| --- | --- | --- |
| `graph_schema_invalid` | 不符合 JSON Schema | 指出字段路径 |
| `node_id_dup` | 节点 id 重复 | 重命名 |
| `dep_missing` | `depends_on` 指向不存在的节点 | 列出合法 id |
| `dep_cycle` | 有环 | 返回环序列 `A→B→C→A` |
| `write_overlap` | 两节点写同一路径 | 合并节点或加串行 |
| `write_outside_repo` | 绝对路径 / 越出仓库 | 用相对根路径 |
| `path_not_normalized` | `./`、`..`、`//` | 规范化后重提 |
| `acceptance_missing` | 缺验收 | 每个节点必须有 |
| `acceptance_trivial` | `exit 0` / `true` / `\|\| true` / `--no-run` | 三层防御见 §6.4 |
| `required_not_in_writes` | `required_files` 不在写集 | 补进 writes |
| `requirement_uncovered` | 需求条目无节点覆盖 | 列出未覆盖条目 |
| `covers_unknown_ref` | 引用不存在的条目 | 列出合法引用 |
| `too_many_files` / `node_too_big` / `too_many_nodes` | 粒度超限 | 再拆或两级拆解 |
| `base_commit_unknown` | 基线不存在 | 用当前 HEAD 重拆 |
| `writes_conflict_active` | 与在途任务写集相交 | 排后或改边界 |
| **`interface_missing`** | `implement` 的祖先没有 `interface` | 补一个 interface 节点 |
| **`interface_ambiguous`** | 同模块多个 interface | 合并为一个 |
| **`interface_write`** | 非 interface 节点写了冻结接口路径 | 删掉这几行 |
| **`test_missing`** | `implement` 的祖先没有 `test` | 补 test 节点 |
| **`test_write`** | 非 test 节点写了测试路径 | 删掉 |
| **`consumes_unknown`** | V7 符号未闭合 | 补 provides 或改签名 |
| **`kind_topology`** | 类型顺序错误（如 test 依赖 implement） | 按 §4.8 重排 |
| **`decision_tampered`** | `decisions[]` 被人之外改了 | 恢复 |

### 6.2 L 组（产物级）

| 层 | 检查 | 谁跑 | 失败 |
| --- | --- | --- | --- |
| **L0 结构** | 路径 ⊆ `writes`；无 `..`/绝对路径/符号链接；单文件 ≤ 2MB；总大小 ≤ 50MB | 平台 | `rejected` |
| **L1 完整** | 重算 sha256；`required_files` 齐全；**冻结文件未被改动**；编码统一 | 平台 | `rejected` |
| **L2 形状** | `schema_output` 过 JSON Schema；linter 零 error | 平台 | `rejected` |
| **L3 行为** | 按 `acceptance.kind` 执行（red/green/full/skeleton） | 终端跑 + 平台按信任分复跑 | `rejected` → 重试 |

L3 的"复跑"不是全量：**信任分决定抽检率**（§7.4）。这是成本与信任之间唯一可调的旋钮。

### 6.3 执行环境

| 场景 | 环境 | 网络 |
| --- | --- | --- |
| 终端本地跑 L3 | 终端自己的机器 | 由终端负责 |
| 平台复跑 L3 | 容器（同 §10.2 规格，但可放宽到 10 分钟） | 默认断网 + 包代理白名单 |
| integration 全量 | 容器（严格规格） | 同上，超时 60 分钟 |

### 6.4 反作弊矩阵（这是平台真正值钱的部分）

| 作弊手法 | 防御 | 层级 |
| --- | --- | --- |
| 实现方改软测试 | 测试独立任务 + 冻结 sha256 + 复跑覆盖 | L1 |
| 写空命令（`exit 0`、`\|\| true`） | 静态黑名单 + `strength` + 复跑看输出 | V3 / L3 |
| 写空洞断言（`assert!(true)`） | **红测试验收**：空洞断言在骨架上通过 → 拒 | L3 |
| 改接口蒙混 | 接口冻结 + 写集拒绝 | V2 / L0 |
| 提交越界文件（写别人的模块） | 路径 ⊆ writes | L0 |
| 用旧基线产物覆盖 | `base_commit` + `stale` + rebase 重提 | L1/L4 |
| 上报假日志 | 平台复跑（按信任分）+ 日志结构校验 | L3 |
| 声称成功 | 只认退出码与测试结果，不认 `status` | L3 |

## 7. 调度

### 7.1 状态机

**任务**

```
queued ──claim──► claimed ──submit──► validating ──pass──► accepted ──► merged
  ▲                  │                   │ fail                    │
  └──lease 过期──────┘                   ▼                        │
  └───────────────────────────── rejected（可重试）                │
                                    │ attempts 超限                │
                                    ▼                             │
                                needs_human                       │
                                                                  │
  accepted ──图修订──► stale ──rebase──► queued                   │
```

**图**

```
draft ──validate──► validated ──approve──► active ──supersede──► superseded
  │                     │
  └── reject ◄──────────┘  → 回 planner 重拆（新 version）
```

规则：
- 只有 `active` 图下的任务可派发；
- 任何修订产生新 `version`，旧版 `superseded`，**永不物理删除**；
- 已 `accepted` 的产物在被修订牵连时标 `stale`，**不删除**，且禁止进入 integration。

### 7.2 认领 SQL（写集互斥必须在这里，不能靠代码旁路）

```sql
WITH candidate AS (
  SELECT t.id
  FROM tasks t
  WHERE t.state = 'queued'
    AND t.kind = ANY($1)                       -- 终端声明的能力
    AND t.tech_stack && $2                     -- 标签交集
    AND NOT EXISTS (                           -- 前驱未 accepted
      SELECT 1 FROM task_deps d JOIN tasks p ON p.id = d.parent_id
      WHERE d.child_id = t.id AND p.state <> 'accepted'
    )
    AND NOT EXISTS (                           -- 写集互斥：在途任务不能与我相交
      SELECT 1 FROM tasks o
      WHERE o.state = 'claimed' AND o.lease_until > now()
        AND o.writes && t.writes
    )
    AND NOT EXISTS (                           -- integration 全局串行
      SELECT 1 FROM tasks g
      WHERE g.kind IN ('integration','repair')
        AND g.state IN ('claimed')
        AND t.kind IN ('integration','repair')
    )
  ORDER BY
    CASE t.kind WHEN 'integration' THEN 2 WHEN 'repair' THEN 3 ELSE 1 END,
    t.priority DESC, t.created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE tasks
SET state = 'claimed', terminal_id = $3, lease_id = $4,
    lease_until = now() + make_interval(secs => $5)
FROM candidate
WHERE tasks.id = candidate.id
RETURNING tasks.*;
```

两个工程要点：

1. `writes` 必须存成 `text[]`（配 GIN 索引），不能用 `jsonb` —— `&&` 是数组交叠运算，jsonb 走不通。
2. 写集互斥是**同一条语句里的谓词**。2.0 的示例 SQL 漏了它、规范里却写了硬约束，这种"文档 A、代码 B"的分歧，实现时一定按代码写。

### 7.3 租约、心跳、检查点、续跑

| 机制 | 规格 |
| --- | --- |
| 租约 | 默认 30 分钟；`claim` 返回 `lease_expires_at`（服务端时钟，终端只读不信任本地钟） |
| 心跳 | 每 5 分钟；返回 `remaining_seconds`；`409 lease_expired` 时终端必须**立即停手且不提交** |
| 过期 | `claimed → queued`，`attempts += 1`（上限 2）→ `needs_human` |
| 检查点 | `POST /v1/checkpoint` 上传中间产物 + 进度 + 备注；最多保留 5 个 |
| 续跑 | 重试时 `claim` 返回 `resume: {checkpoint_id, artifacts[], hint}`，终端可从半成品继续 |
| 幂等 | `submit` 按 `(task_id, lease_id, attempt)` 幂等；重复提交返回首个结果，不重复计入 |

**检查点解决的是"90 分钟白干"**：租约只保证锁不死，不保证工作不丢。终端崩了之后，下一次 attempt 至少能看到半成品。

### 7.4 信任分与抽检

```
trust = 该终端最近 20 次提交中「一次通过」的比例
```

| 条件 | 复跑比例 |
| --- | --- |
| 新终端（< 5 次提交） | 100% |
| trust ≥ 0.95 且 n ≥ 20 | 5% |
| trust ≥ 0.90 | 20% |
| 其它 | 50% |

复跑未通过的样本**不直接判死**（可能是环境差异），而是降 trust 并要求人工复核。没有这个旋钮，你要么全量复跑（变成 CI 农场），要么完全信任（等于没验收）。

### 7.5 热文件策略（决定适用范围）

注册表、路由表、`mod.rs`、`package.json`、DI 容器——任何新模块都要动它们。三种策略按优先级：

1. **消除**：用约定式自动发现（glob 扫描、`import.meta.glob`、entrypoint 目录），让新增模块不需要改任何中心文件。**这是唯一真正的解法**，应该在写代码之前就做。
2. **隔离**：设计一个 `registrar` 任务，`writes` 只包含这些中心文件，放在图末尾串行执行。代价是它成为瓶颈。
3. **追加合并**：允许在这些文件里放标记区间：

   ```rust
   // openvow:append:routes
   // openvow:end
   ```

   多个任务可以往自己的区间追加，由 integration 任务按确定性顺序拼接。平台只做拼接，不改内容。

如果三种都做不到，这个项目不适合 OpenVow——那是 scope guard 的问题，不是设计的问题。

## 8. 协议 v3

### 8.1 端点总表

| 方法 | 路径 | scope | 说明 |
| --- | --- | --- | --- |
| POST | `/v1/claim` | terminal | 原子认领（含写集互斥） |
| POST | `/v1/heartbeat` | terminal | 续租 |
| POST | `/v1/checkpoint` | terminal | 中间产物 |
| POST | `/v1/submit` | terminal | 提交结果与证据 |
| PUT | `/v1/artifacts/{sha256}` | terminal | 上传二进制（先传后提交） |
| GET | `/v1/artifacts/{sha256}` | terminal | 下载（含上游产物） |
| GET | `/v1/tasks/peek` | any | 只看不拿（看板/调试） |
| POST | `/v1/graphs` | terminal(planner) | 提交图草案 |
| GET | `/v1/graphs/{id}` | any | 读图 |
| POST | `/v1/graphs/{id}/validate` | terminal | 重跑 V1–V8 |
| POST | `/v1/graphs/{id}/approve` | **human** | 批准（生成新 version） |
| POST | `/v1/graphs/{id}/reject` | **human** | 驳回 + reason |
| POST | `/v1/terminals` | admin | 发 token |
| DELETE | `/v1/terminals/{id}` | admin | 吊销 |

**权限必须写死在表里**：planner 拿不到 `approve`；执行终端拿不到 `graphs/approve`；integration 的 claim 资格由 `kind` 决定，不由 token 决定。

### 8.2 关键报文

**claim → 200**

```json
{
  "task_id": "N-03-7f21",
  "kind": "implement",
  "lease_id": "L-9c2e",
  "lease_expires_at": "2026-10-21T21:10:00Z",
  "attempt": 1,
  "repo_url": "ssh://openvow/proj-14.git",
  "base_commit": "9c1f3ab",
  "writes": ["src/parser/impl/**"],
  "reads": ["src/parser/mod.rs", "tests/parser/**"],
  "frozen": [
    { "path": "src/parser/mod.rs", "sha256": "…" },
    { "path": "tests/parser/basic.rs", "sha256": "…" }
  ],
  "acceptance": { "kind": "green_tests", "run": "cargo test --locked parser" },
  "audit_rate": 0.2,
  "resume": null
}
```

`frozen` 是**给终端看的约束**，不是信任它的依据——L1 会自己重算。

**submit → 200**

```json
{
  "task_id": "N-03-7f21",
  "lease_id": "L-9c2e",
  "attempt": 1,
  "base_commit": "9c1f3ab",
  "files": [{ "path": "src/parser/impl/mod.rs", "sha256": "…" }],
  "evidence": {
    "exit_code": 0,
    "tests_total": 24,
    "tests_passed": 24,
    "log_snippet": "…",
    "duration_s": 214
  },
  "env": { "harness": "claude-code/2.x", "model_family": "…", "prompt_hash": "…" }
}
```

`evidence` 是声明，不是结论；结论来自 L3 的复跑与退出码。

### 8.3 错误码

| 码 | HTTP | 含义 | 终端应做 |
| --- | --- | --- | --- |
| `lease_expired` | 409 | 租约被回收 | 停手，丢弃本地改动 |
| `write_conflict` | 409 | 写集与在途任务冲突 | 换任务 |
| `deps_unmet` | 409 | 前驱未 accepted | 换任务 |
| `frozen_file_modified` | 422 | 动了冻结文件 | 还原后重提 |
| `path_outside_writes` | 422 | 提交了写集外文件 | 删除后重提 |
| `acceptance_failed` | 422 | L3 未通过 | 修正后重试（计入 attempts） |
| `schema_invalid` | 422 | L0–L2 失败（带 `violations[]`） | 修正后重提 |
| `rate_limited` | 429 | 并发/频率超限 | 退避 |

### 8.4 接入方式：MCP 适配器优先

**这是最容易低估的一块。** Claude Code、DSH 都是批处理式 CLI：给一段提示，跑完退出，**不会每 5 分钟调你的 heartbeat**。

所以接入不是"写一段 System Prompt"，而是：

| 形态 | 适用 | 说明 |
| --- | --- | --- |
| **MCP server（首选）** | Claude Code、支持 MCP 的 Harness | 暴露 `claim / heartbeat / checkpoint / submit / upload` 五个工具，agent 自己在循环里调用 |
| CLI wrapper | 只接受命令行的 Harness | `openvow run -- <harness command>`，wrapper 负责续租、收产物、提交 |
| 原生 SDK | 自研 Agent | 直接调 HTTP |

MCP 工具签名示例：

```
openvow_claim(kinds: string[]) -> {task, lease, repo, frozen[], resume}
openvow_heartbeat(lease_id) -> {remaining_seconds}
openvow_checkpoint(lease_id, files[], note) -> {checkpoint_id}
openvow_submit(lease_id, files[], evidence) -> {accepted, violations[]}
```

一份可用的 glue prompt（很长，但核心就三句）：

```
你有 OpenVow 任务。先用 openvow_claim 领活；工作期间每 5 分钟 openvow_heartbeat；
每完成一个可编译的中间状态就 openvow_checkpoint；最后 openvow_submit。
不得修改 lease 里 frozen 列出的任何文件——平台会用冻结版本覆盖它们，改了等于没改。
```

**结论**：协议容易抄，适配器不容易。适配器才是产品的一部分。

## 9. 产物与集成

### 9.1 产物库

- 内容寻址（sha256），只追加、不覆盖；
- 目录结构：`artifacts/{sha256前2位}/{sha256}`，与原路径解耦（路径放在索引里，防止"换个目录名就绕过校验"）；
- 每个产物行记录：`task_id, attempt, path, size, media_type, created_at, terminal_id`；
- 可按 `task + attempt` 回溯，支持"这个文件是谁在哪次尝试里交的"。

### 9.2 集成任务的执行规格

```
输入：group_id、按 DAG 排序的 accepted 任务列表、各自产物、canonical head
步骤：
  1. clone canonical head 到临时工作区
  2. 按 DAG 顺序逐个 apply（文件覆盖，不做三方合并——写集不相交，理论上不会冲突）
  3. 若出现意外冲突（写集校验有 bug）→ 立即失败，报 `unexpected_overlap` 告警
  4. 生成 candidate_commit
  5. 容器内：install → build → test（全量）
  6. 通过：fast-forward 推主干；失败：打包失败包
输出：merged | failed(bundle)
```

**时间上限**：60 分钟；超时按失败处理，但标记 `timeout`，不生成 repair（可能是环境问题，先人工看）。

### 9.3 repair 环路

```
integration failed
      │
      ▼
失败包 = { candidate_commit, 失败测试名[], 日志片段, 涉及 diff, 上次通过的 commit }
      │
      ▼
repair 任务（不同终端优先）→ accepted
      │
      ▼
integration 重跑（attempt+1，最多 3 次）
      │
      └─ 仍失败 → needs_human + 图级告警
```

**为什么单独建任务而不是让 integration 重试**：修复需要有人对"语义冲突"做判断，重试同样的输入只会得到同样的失败。失败包就是修复任务的上下文。

### 9.4 合并顺序与 git 拓扑

- canonical 分支按 `integration` 完成顺序线性推进（fast-forward only，禁止 force push）；
- 每个 integration 产生一个 merge commit，message 里带 `group_id` 与任务列表；
- 回滚 = revert 那个 merge commit，任务回到 `stale`，不删除产物；
- 终端永远只读 canonical，写权限只属于集成流程。

## 10. 安全

### 10.1 三种凭证

| 凭证 | 持有者 | 用途 | 是否违反"不持模型凭证" |
| --- | --- | --- | --- |
| 模型 API Key | 终端 | 调模型 | 不涉及，平台永不见 |
| 终端 token | 平台签发 | 调 OpenVow | 不违反（这不是模型凭证） |
| 提交签名（可选） | 终端私钥 | 证明来源 | 不违反 |

**平台必须持有终端 token**，否则任务池可被任意投毒。2.0 之前那句"平台不持有任何密钥"必须永久废除。

### 10.2 集成容器：这是 RCE 面

在容器里跑终端提交的 `build.rs` / `npm install` / `Makefile`，等于让陌生代码在你的机器上执行。规格（缺一不可）：

| 项 | 规格 |
| --- | --- |
| 网络 | 默认 `--network=none`；需要装依赖时走只读包代理（白名单域名） |
| 文件系统 | rootfs 只读；工作区可写；`tmpfs` 做 home 与临时目录 |
| 用户 | 非 root（uid 1000），`--cap-drop=ALL` |
| 隔离 | seccomp 默认配置；禁止挂载 docker.sock；禁止 `--privileged` |
| 资源 | 2 CPU / 4GB / 60 分钟 / 磁盘配额 5GB |
| 宿主 | 理想情况独立 runner 节点，与数据库网络隔离 |
| 镜像 | 固定 digest，任务日志里记录，便于复现 |

**注意**：`npm install` 的 postinstall 脚本本身就是任意代码执行，白名单代理必须只放行包下载，不代理任意域名。

### 10.3 审计字段

每个产物必须能回答五个问题：谁、何时、基于什么、用什么模型、通过了什么。

| 字段 | 来源 | 可信度 |
| --- | --- | --- |
| `terminal_id` | 平台（token 推导） | 高 |
| `task_id / attempt` | 平台 | 高 |
| `base_commit` | 平台记录 | 高 |
| `harness / model_family / prompt_hash` | 终端自报 | 低（但比没有强） |
| `acceptance_result` | 平台复跑或终端声明 | 分档记录（`self_reported` / `replayed`） |

自报字段一律标 `unverified`，看板上与复跑结果区分显示。

## 11. 成本模型

| 成本项 | 量级 | 关键影响因素 |
| --- | --- | --- |
| 拆解（每项目一次） | 150k–400k tokens | 仓库规模、需求清晰度 |
| 接口 + 测试（每模块） | 40k–120k tokens | 模块复杂度；**这部分是新增成本** |
| 实现（每任务） | 20k–80k tokens | 上下文大小、重试次数 |
| 平台复跑 | 每次 1–10 分钟 CPU | 信任分越低越多 |
| 集成全量 | 5–60 分钟 CPU | 项目规模、测试套件 |
| 人工评审 | 5–15 分钟/任务 | 图审批 + 抽样产物 |

**3.0 相比 2.1 增加了"接口 + 测试"两项前置成本**，大约占单模块总 token 的 25–35%。这是有意的：

> 用 30% 的前置成本，换掉"集成阶段全盘返工"的风险。分布式开发里，返工的成本是前置成本的 5–10 倍。

如果连这 30% 都不愿意付，那就别并行——直接一个人顺序做。

## 13. 路线图

### M0 · 单终端闭环（1–2 周）— 这是真正的产品

范围：手工建任务，CLI 操作，一个终端，无图、无并行。
任务类型：`interface → test → implement`，手工串。

验收标准：
1. 三个任务串起来，最后一个 `accepted`；
2. 终端改了测试文件 → `frozen_file_modified` 拒绝；
3. 空洞测试（`assert!(true)`）→ 红测试验收失败；
4. 越界写文件 → `path_outside_writes` 拒绝；
5. 一个任务的产物可按 sha256 回溯到 terminal + 时间 + attempt。

**M0 不并行，但它已经是完整的产品**：契约 + 验收 + 冻结 + 归集。后面所有东西都是在它之上加并发。

### M1 · 图与契约（2–3 周）

范围：`decompose` + planner 终端 + V1–V8 + 人审 + `approve`。
验收：一张 5 节点图能过校验并派发；写集冲突、接口缺失、类型拓扑错误各能被 V 组拦住；驳回后 planner 能拿到 reason 重拆。

### M2 · 并行与信任（2 周）

范围：多终端、写集互斥 SQL、租约/心跳/检查点、信任分抽检、token 吊销。
验收：10 个终端并发抢 10 个任务，0 重复、0 写集相交；`kill -9` 后 60s 内回队列且 attempts+1；检查点可续跑。

### M3 · 集成与修复（2–3 周）

范围：integration 任务自动物化、容器全量验证、失败包、repair 环路、canonical repo 合并。
验收：故意让两个任务语义冲突，集成失败 → 自动生成 repair → 修复后合并成功；integration 连续失败 3 次升级 `needs_human`。

### M4 · 规模化（按需）

范围：两级拆解、merge group 分片、看板、许可证扫描、成本统计。

## 14. 关键决策记录（ADR）

| # | 决策 | 否决的方案 | 理由 |
| --- | --- | --- | --- |
| 01 | 拉模式（终端 claim） | 推模式（平台调用终端） | 风控与成本必须留在终端 |
| 02 | 平台不内置任何模型 | 内置拆解/审查 Agent | 一旦内置，边界破，平台变成中心化服务商 |
| 03 | Postgres `SKIP LOCKED` | Redis 分布式锁 / Celery / Prefect | 一条 SQL 解决，少一个中间件 |
| 04 | 内容寻址产物库 | 按任务存目录 | 去重、可回溯、防路径绕过 |
| 05 | 拆解也是任务 | 平台内置 planner | 保持不变量；planner 可以是更强的账号 |
| 06 | 接口前置为独占任务 | 靠 `decisions[]` 口头约定 | 文件不相交 ≠ 语义能对接 |
| 07 | 测试独立 + 红测试验收 + 冻结 | 实现方自带测试 | 否则验收可被自己判卷 |
| 08 | 集成是任务，不是阶段 | L4 作为流水线阶段 | 失败需要工作载体，否则流程停摆 |
| 09 | MCP 适配器优先 | 一段 System Prompt | 批处理 CLI 无法定时心跳 |
| 10 | 匿名只在协议层 | 真匿名 | 私有项目需要追责与质量治理 |
| 11 | 风控叙事降级为附带好处 | 以"防封号"为核心卖点 | 套利不可持续 |
| 12 | 校验只有四层，合并是任务 | L0–L4 五层 | 合并需要判断，不能是机械阶段 |
| 13 | 平台只决定顺序，不改字节 | 平台做自动修复 | 改字节就破坏了"零二次加工"的承诺 |

## 15. 未决问题

1. **merge group 怎么切？** 默认整图一个；大图按模块拆成多个 group 并行集成，但跨 group 的接口一致性会退化成"组间集成"。需要实测决定阈值（节点数 > 12？跨目录 > 3？）。
2. **红测试的 `min_failing_ratio` 定多少？** 0.8 是拍的。有些模块天然有一半是类型测试，会在骨架上通过。可能需要按 `kind` 或语言分档。
3. **repair 的写集要不要放开到全仓？** 放开能修得动，但会破坏"写集可控"的直觉；不放开则修不了跨模块问题。倾向：默认放开，但 repair 产物必须人工过目。
4. **信任分会不会惩罚慢工出细活的终端？** 一次通过率奖励"稳"，可能抑制"敢重构"的终端。需要观察，必要时加"返工率"作为第二维。
5. **是否支持从 issue tracker 直接建需求？** 会显著降低使用门槛，但会把"需求条目化"这件苦活外包给外部系统，条目质量不可控。

## 16. 术语表

| 术语 | 含义 |
| --- | --- |
| 需求条目（requirement item） | 需求文档里带稳定 id 的最小可验证单元，`covers` 引用它 |
| 图（graph） | 一张 `task_graph.json`，描述一次需求的全部任务与依赖 |
| merge group | 一起合并的一组任务，默认整图，可拆 |
| 契约（contract） | 任务的写集、接口、验收、覆盖，四件套 |
| 冻结（frozen） | 接口与测试在 accepted 后不可再改，平台以其哈希为准 |
| 红测试（red tests） | 在骨架上必须失败的测试，用来证明它不是空测试 |
| 一次通过（first-pass） | 首次提交即 accepted，不消耗 attempts |
| 集成任务（integration） | 把 group 产物按序应用并全量验证的任务 |
| 失败包（failure bundle） | 集成失败时生成的上下文，作为 repair 任务的输入 |
| canonical repo | 平台维护的唯一主干，只有集成流程可写 |
| 信任分（trust） | 终端近 20 次提交的一次通过率，决定平台复跑比例 |

## 17. 一句话收尾

**1.0 想的是"把活分出去"，2.x 补的是"收回来能用"，3.0 补的是"怎么保证分出去的时候，接口已经说清楚、判卷的人不是考生、合并失败有人接活"。**

分布式开发真正的难点从来不是并发，是**契约**和**责任的落点**。这份设计里，每一件产出内容的事都有人负责，而且负责的人不是同一个人。
