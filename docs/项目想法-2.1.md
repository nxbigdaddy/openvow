# OpenVow 设计 2.1：拆解层

> ⚠️ **本文已被《[项目想法-3.0](项目想法-3.0.md)》取代**，仅作历史归档。拆解层的最终形态（含接口前置、红测试、集成任务）以 3.0 为准。
>
> 对《项目想法-2.0》的增量修订。2.0 回答"活怎么分出去、怎么收回来"，本文回答"**活是怎么被切出来的**"。
> 其余部分仍以 2.0 为准；被本文取代的条目见第 12 节「修订索引」。

---

## 1. 结论先行

**拆解当然要用模型/Agent 做，但绝不能由平台来跑。**

一旦平台内置拆解模型，2.0 的地基（不持有模型凭证、不主动调用、风控分散）当场失效——只是把风控重新集中回平台，换了个叫"拆解"的接口。

正确的形态是：**把拆解本身变成一个任务**。

```
人发布 meta 任务（decompose）
        ↓
planner 终端（自带强模型账号，标签 planner）POST /v1/claim 拉走
        ↓
产出 task_graph.json —— 结构化 DAG，不是自然语言
        ↓
平台 graph-validator 做 V1–V6 结构校验（纯函数，不调模型）
        ↓
人审 approve（只看 diff）→ 图生效 → 子任务进 queued
```

这套设计不新增任何运行时服务，只新增：一个任务类型、一个产物类型、一张表、一个校验器。

---

## 2. 为什么拆解必须由人兜底

这是本文最重要的一条，也是唯一不能"工程化"掉的部分：

> **拆解的产物就是验收标准本身。没有比验收标准更高阶的标准，可以用来验证它。**

代码任务有 `cargo test` 当裁判；拆解任务的裁判是谁？

| 你能自动做的 | 你无法自动做的 |
| --- | --- |
| 依赖无环 | 模块边界划得对不对 |
| 写集不相交 | 这个切分粒度是否符合工程直觉 |
| 每个节点有验收命令 | 验收命令能否真正证明需求被满足 |
| 需求条目被 covers 覆盖 | covers 是"真做了"还是"贴标签" |

所以拆解层只能做到：**机器保证结构合法，人保证方案正确**。人审不是流程冗余，是唯一的正确性来源。

推论：拆解层的人审界面必须极其省力（第 7 节）。人一旦要"重读全文再理解"，他就变成了二次加工者，平台的设计前提就崩了。

## 3. 三个成本事实（别自欺）

**① 拆解是整条链上最贵的一步，而且不能并行。**
它需要全仓上下文、必须用最强的模型、天然串行。所谓"分布式省成本"，摊开的只是中低难度的执行，最贵的这一步反而更集中了。

**② 拆解失败的成本是 O(整个项目)。**
执行任务失败，重试一个任务；拆解失败，整张 DAG 报废，下游全废。所以图必须版本化、可回滚（第 8 节）。

**③ 拆解 Agent 需要的上下文，比执行 Agent 大一个数量级。**
它要 repo map、要现有约定、要历史任务模板。这决定了它必须是本地终端（自己 clone 仓库），而不是"平台把代码喂给模型"——后者会把 2.0 刚立起来的边界再捅破。

量级参考（仅用于决策，不作为承诺）：

| 项 | 单次量级 | 说明 |
| --- | --- | --- |
| 拆解一次（中型项目） | 150k–400k tokens | 全仓地图 + 需求 + 多轮自检 |
| 执行单个任务 | 20k–80k tokens | 上下文限定在写集附近 |
| 20 任务的执行总计 | 0.4M–1.6M | 可并行 |
| 拆解占比 | 10%–25% | 但它串行、且必须用强模型 |

## 4. 三种落地形态

| 形态 | 谁跑模型 | 守住 2.0 不变量 | 拆解质量 | 结论 |
| --- | --- | --- | --- | --- |
| A. 平台内置拆解 Agent | 平台 | ❌ | 高 | 不做 |
| B. planner 终端拉 meta 任务 | 终端 | ✅ | 中高 | 目标形态（M1.5） |
| C. 人在 IDE 里和 Agent 一起拆 | 人自己的工具 | ✅ | 最高 | **M0 就走这个** |

**M0 不写任何拆解代码**，人工拆、手工 `POST /v1/tasks`。理由不是偷懒：

> 拆解 Schema 的形状，只能从"执行侧的真实失败模式"里长出来。先做 B 再做执行，你会设计出一套漂亮但 Agent 根本遵守不了的契约。

先跑通 5–10 个手工任务，记下每次返工的原因，那些原因就是 planner 的约束清单。

## 5. 领域模型增量

### 5.1 新增表

```sql
graphs(
  id, project_id, version, state,
  requirement_ref,            -- 需求文档标识（非内容）
  base_commit,                -- 拆解所依据的代码基线
  graph_json,                 -- 完整正文，不可变，内容寻址
  graph_sha256,
  created_by_terminal,        -- planner 终端
  approved_by, approved_at,   -- 人（必需的字段）
  supersedes,                 -- 上一版 graph id
  created_at
)

graph_violations(graph_id, code, node_id, message, at)  -- 校验记录，只追加

graph_amendments(graph_id, node_id, field, before, after, by, at)  -- 人审改动，用于回灌 prompt
```

### 5.2 `tasks` 表增加字段

```sql
graph_id, node_id, covers jsonb
```

`covers` 是需求条目引用数组，与第 6 节的 V4 校验对应。

### 5.3 图的状态机

```
draft ──validate──► validated ──approve(人)──► active ──supersede──► superseded
  │                     │
  └── reject(人) ◄──────┘
        │
        └─► 回到 planner 重拆（新建 version，不覆盖旧图）
```

规则：

- 只有 `active` 图下的 `queued` 任务可被派发。
- `validate` 是纯函数，可反复跑，不产生状态副作用（除了记录 violations）。
- `approve` **必须** 由 human token 调用；planner token 无此权限（第 7 节）。
- 任何修改都产生新 `version`，旧版转 `superseded`，**永不物理删除**。

## 6. 契约：`task_graph.json`

### 6.1 完整示例

```json
{
  "schema": "graph/v1",
  "requirement": {
    "ref": "R-2026-014",
    "title": "表达式解析器",
    "base_commit": "9c1f3ab"
  },
  "nodes": [
    {
      "id": "N-01",
      "title": "AST 与解析入口",
      "summary": "实现 src/parser 的入口函数与 AST 节点定义",
      "writes": ["src/parser/**"],
      "reads": ["src/lib.rs", "docs/parser.md"],
      "tech_stack": ["Rust"],
      "depends_on": [],
      "covers": ["R-2026-014/1.1", "R-2026-014/1.2"],
      "acceptance": {
        "build": "cargo build --locked",
        "test": ["cargo test --locked parser"],
        "strength": "strong",
        "timeout_s": 900
      },
      "est": { "files": 3, "diff_lines": 260 },
      "notes": "先只支持算术表达式，函数调用留到 N-02"
    }
  ],
  "decisions": [
    {
      "id": "D-1",
      "text": "手写递归下降，不引入 lexer 生成器",
      "affects": ["N-01"]
    }
  ],
  "uncertain": [
    "需求 3.2 未说明错误恢复策略，暂按 panic-free 处理"
  ]
}
```

设计取舍：

- **不存 `edges`**。依赖只写在 `depends_on` 里，边由它推导。两处存同一事实必然漂移。
- **`decisions[]` 是人的领地**。架构选型（用什么解析器、模块怎么分）由人预先给定，planner 只负责"在既定架构下切分"。这是防止 planner 越权做架构决策的硬边界。
- **`uncertain[]` 是逃生口**。让 planner 承认不确定，比逼它编造一个"看起来完整"的图要好——不确定项会出现在人审界面的顶部。
- **`est` 不是承诺，是粒度信号**，供 V5 校验用。

### 6.2 粒度硬约束

| 约束 | 阈值 | 违反后果 |
| --- | --- | --- |
| 单节点写文件数 | ≤ 4 | V5 拒绝 |
| 单节点预估 diff | ≤ 400 行 | V5 拒绝 |
| 单图节点数 | ≤ 12 | V5 拒绝，提示做两级拆解 |
| 节点必须可被单次 claim 完成 | 主观但强制 | 人在 approve 时判断 |

## 7. 协议增量（5 个端点）

### 7.1 `POST /v1/graphs` — planner 提交草案

```json
// 请求
{
  "requirement_ref": "R-2026-014",
  "base_commit": "9c1f3ab",
  "node_claim": { "task_id": "T-20261021-0001", "lease_id": "L-7f3a..." },
  "graph": { "...": "见 6.1" }
}

// 201
{ "graph_id": "G-0007", "version": 1, "state": "draft",
  "violations": [], "next": "/v1/graphs/G-0007/validate" }
```

- **幂等**：以 `sha256(requirement_ref + base_commit + graph_json)` 去重。重复提交返回已有 graph（200）。
- 提交即自动跑一次 validate，`violations` 随响应返回，planner 不必再单独请求。
- 草案不占任务池，未 approve 的图对执行终端不可见。

### 7.2 `POST /v1/graphs/{id}/validate` — 显式重跑

```json
// 200（无论是否通过，HTTP 都是 200；结论在体中）
{
  "graph_id": "G-0007",
  "passed": false,
  "violations": [
    { "code": "write_overlap", "node_id": "N-02",
      "message": "N-02 与 N-03 都写 src/parser/mod.rs",
      "hint": "合并两个节点，或给 N-03 增加 depends_on: [N-02]" }
  ]
}
```

`hint` 是给 planner 重试用的，必须是人话 + 可执行动作。校验器写不好 `hint`，planner 就只能瞎猜，重试三轮后放弃。

### 7.3 `POST /v1/graphs/{id}/approve` — 人审通过（human token）

```json
{
  "approver": "human:alice",
  "notes": "把 N-03 的写集从 src/** 收窄到 src/parser/error/**",
  "amendments": [
    { "node_id": "N-03", "field": "writes",
      "before": ["src/**"], "after": ["src/parser/error/**"] }
  ]
}
```

- 每次 approve 生成新 `version`；`amendments` 逐条落 `graph_amendments`。
- 这些 amendments 是后续提升 planner prompt 的训练材料（第 11 节）。

### 7.4 `POST /v1/graphs/{id}/reject` — 驳回重拆

```json
{ "approver": "human:alice", "reason": "N-01/N-02 边界错误：AST 定义应在 N-02", "retry": true }
```

`retry: true` 时平台把 meta 任务重新入队，并把 reason 注入 planner 的下一次输入（失败→反馈→重拆的闭环）。

### 7.5 `GET /v1/graphs/{id}?version=latest`

只读，供看板与人审界面使用；返回节点列表 + 覆盖矩阵 + 写集热力所需的聚合数据。

### 7.6 权限模型（新增）

| token scope | 能做什么 |
| --- | --- |
| `terminal` | claim / heartbeat / submit / artifacts / `POST /v1/graphs` / validate |
| `human` | 上述 + `approve` / `reject` / 任务契约修改 |
| `admin` | 上述 + 发 token / 吊销 / 优先级调整 |

**planner 终端拿不到 approve 权限**——这条要写死在权限表里，不能靠"约定"。

## 8. 校验器 `graph-validator`

纯函数：输入 `graph_json` + 仓库元数据（在 `base_commit` 上的文件清单），输出 `violations[]`。**不调用任何模型**，因此可以无限次重跑。

| 组 | 码 | 检查 | 典型 hint |
| --- | --- | --- | --- |
| V1 结构 | `graph_schema_invalid` | 不符合 JSON Schema | 指出具体字段路径 |
| | `node_id_dup` | 节点 id 重复 | 重命名 |
| | `dep_missing` | `depends_on` 指向不存在的节点 | 列出合法 id |
| | `dep_cycle` | 有环 | 返回环上的节点序列 `A→B→C→A` |
| V2 所有权 | `write_overlap` | 两节点写同一路径 | 合并节点，或加串行依赖 |
| | `write_outside_repo` | 写到仓库外 / 绝对路径 | 必须是相对仓库根的路径 |
| | `path_not_normalized` | 含 `./`、`..`、`//` | 规范化后重提 |
| | `write_target_missing_dir` | 目标目录不存在且不属于任何节点创建 | 补一个创建节点的写入声明 |
| V3 完备 | `acceptance_missing` | 无 build/test | 每个节点必须有验收命令 |
| | **`acceptance_trivial`** | 命令是 `exit 0` / `true` / `|| true` / `; true` / `set +e` | 这是最常见的造假，见下方说明 |
| | `acceptance_compile_only` | 只有 build 没有 test | 允许，但标记 `strength: compile`，需人工放行 |
| | `required_not_in_writes` | `required_files` 不在 `writes` 内 | 补进 writes |
| V4 覆盖 | `requirement_uncovered` | 需求条目无节点覆盖 | 列出未覆盖条目 |
| | `covers_unknown_ref` | 引用了不存在的需求条目 | 列出合法引用 |
| V5 粒度 | `too_many_files` | 单节点 > 4 文件 | 再拆 |
| | `node_too_big` | 预估 diff > 400 行 | 再拆 |
| | `too_many_nodes` | 单图 > 12 节点 | 建议两级拆解（第 9 节） |
| V6 基线 | `base_commit_unknown` | 基线不存在 | 用当前 HEAD 重拆 |
| | `writes_conflict_active` | 与 active 图中的在途任务写集相交 | 排到该任务之后，或改边界 |

**关于 `acceptance_trivial`**（这条值得单独说）：

Agent 会本能地找"能让校验通过"的最短路径。如果验收命令由它写，它完全可以写 `"test": ["true"]`，然后一路绿灯。防御是三层的：

1. 静态黑名单（上表），正则匹配 `exit 0`、`|| true`、`; true`、`set +e`、`cargo test --no-run`、`pytest --collect-only` 等；
2. `strength` 分级：只有 `strong`（真的跑测试）能解锁下游，`compile` 只能解锁到"待人工确认"；
3. L3 复跑抽检：平台在容器里跑一遍，命令是否真跑得动、是否真的执行了测试，看输出而不是看退出码。

## 9. 两级拆解（大项目）

当需求超过约 2000 字、涉及 3 个以上目录、或预估任务数 > 20 时，单张图必然爆掉（节点 > 12 或 planner 上下文不够）。

处理方式：**先拆模块，再拆任务**。

```
L1 图：节点 = 模块（"解析器"、"CLI 层"、"序列化"）
   ↓ 每个模块单独跑一次 decompose（子图）
L2 图：节点 = 可执行任务（≤ 4 文件、≤ 400 行）
   ↓ 平台把 L2 图展开进任务池，父节点变成一个虚拟的"模块完成"闸门
```

- L1 图必须由人审（架构级决策，责任最大）。
- L2 图可以批量审：同一模块内的节点风格一致，人审成本边际递减。
- 触发阈值写进配置，不要写死在代码里——不同项目的合适粒度不一样。

## 10. MVP 修订

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| **M0** | **人工拆解**，CLI 直接 `POST /v1/tasks`；不写 graph 代码 | 手工 5 个任务跑通 claim→submit→accepted 闭环；记录每次返工原因 |
| **M1** | 单图闭环：graphs 表 + V1/V2/V3 校验 + 人审 approve | 手工写一张 5 节点图，能过校验并成功派发；写集冲突能被 V2 拦住 |
| **M1.5** | planner 终端 + V4/V5 + 驳回闭环 | 真实需求一次产出**通过 V1–V3 的比例 ≥ 70%**；人工修改 ≤ 30% 的节点；改图耗时 ≤ 30 分钟 |
| **M2** | 修订/回滚 + 多终端 + 图状态机完整态 | 改一张已 active 的图，已 accepted 的节点标 stale 且阻止 L4 合并 |
| **M3** | 两级拆解 + amendments 回灌 prompt | 20 任务的项目能自动分成 L1/L2 两层并通过人审 |

关键顺序：**M0 的人工拆解不是临时方案，是数据来源**。M1.5 的 planner prompt 应该从 M0 的返工记录里长出来。

## 11. 修订与回滚（拆错了怎么办）

真实项目里必然要改图。三种场景，三种处理：

| 场景 | 触发 | 处理 | 对已 accepted 产物 |
| --- | --- | --- | --- |
| A. 验收命令跑不通 | 执行时发现 `cargo test --locked` 一直失败 | 只改 `acceptance`，新 version，不重拆 | 无影响 |
| B. 写集边界划错 | 两个任务反复冲突 | 新 version 调整 `writes`，必要时加/删依赖边 | 涉及节点标 `stale`，要求 rebase 重提 |
| C. 方向性错误 | 人审发现模块划分根本不对 | 新 version 全量替换，旧图 superseded，未开始的节点 cancel | 全部标 `stale`，**不删除** |

硬规则：

- **已 accepted 的产物永不删除**，只标 `stale`；`stale` 的产物禁止进入 L4 合并。
- 图版本可 diff：输出"新增 / 删除 / 改动的节点"，人审只看 diff，不看全文。
- 修订必须带 `reason`，落入 `graph_amendments`，作为 planner 的负样本库。

**回灌闭环**：每次人审改动都记录"planner 原稿 → 人的修改"。积累 20–30 条后，把它们作为 few-shot 例子塞回 planner 的 System Prompt，比调参有效得多。

## 13. 拆解层风险清单

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| **过度拆分** | 1 个文件拆成 5 个任务，合并成本爆炸 | V5 粒度校验；统计"每 accepted 任务的平均 diff 行数"，过低就告警 |
| **验收造假** | 写 `true` / `exit 0` / `--no-run` 骗过校验 | 静态黑名单 + strength 分级 + L3 容器复跑 |
| **写集划太细** | 为了不冲突把文件拆到目录级，导致串行 | 统计图的"理论并行度"，低于 2 就提示重拆 |
| **人审疲劳** | 图一大，人就开始点"全部批准" | 默认只展开改动的节点；`uncertain[]` 置顶；单次审批 ≤ 12 节点 |
| **planner 越权做架构** | 自行决定模块划分 | `decisions[]` 由人预置，校验"新增决策必须走人审" |
| **覆盖造假** | `covers` 贴了标签但没真做 | 只信 L3 验收，不信 covers；covers 只用于查漏 |
| **上下文不足** | planner 只看需求不看代码，切出无法实现的图 | 强制 `base_commit` + repo map 入参；V6 校验基线存在 |
| **图漂移** | 需求改了，图还是旧的 | 需求文档带 hash，变更即提示"是否重拆" |

## 14. planner 终端接入契约

**输入**（平台随 claim 返回，或终端自行从仓库读取）：

- `requirement`：需求文档（结构化，带 `items[]` 条目号，供 covers 引用）
- `repo_map`：目录树 + 文件行数 + 主要符号（可由终端本地生成，平台不必提供）
- `conventions`：命名/目录/依赖规范（项目级配置）
- `decisions[]`：已定架构决策（人给的，不可推翻）
- `examples[]`：历史 graph 片段（正例）与被人改过的片段（负例）

**输出**：`task_graph.json`，仅此一件，不带解释文字。

**System Prompt 要点**（可直接用）：

```
你是 OpenVow 的拆解终端（planner）。你的产出不是代码，是一份 task_graph.json。

硬约束（违反即校验失败，产出会被驳回）：
1. 每个 node 必须有可执行的 acceptance（build + test），
   禁止 exit 0 / true / || true / --no-run 之类的空命令。
2. 不同 node 的 writes 不得相交。确需共享文件：合并节点，或加 depends_on 串行。
3. 单 node ≤ 4 个文件、≤ 400 行 diff、单图 ≤ 12 个节点。超出就继续拆或声明两级拆解。
4. 每个需求条目至少被一个 node 的 covers 覆盖。覆盖不了的写进 uncertain[]，不要硬编。
5. 不要做架构决策。模块划分与选型已由 decisions[] 给定，你只负责在其下切分。
6. 只输出 JSON，不要解释，不要 markdown 代码围栏。
```

**终端侧要求**：

- 图级任务租约 2 小时（拆解比执行久），心跳照常。
- planner 的失败重试独立计数（`planner_attempts`，默认上限 3），**不消耗节点任务的 attempts**。
- `reject` 后重拆时，平台把 `reason` 注入下一次输入，这是唯一的学习信号。

## 15. 未决问题

1. **`repo_map` 由谁生成？** 终端自己 `git ls-files` + 统计，还是平台提供一个标准化摘要接口？前者简单、后者一致。倾向后者，但要防止它变成"平台把代码传给模型"的口子——只传元数据（路径、行数、符号名），不传内容。
2. **approve 能否批量？** 12 节点以内逐条可以接受；超过就必然变成"批量点击"。是否允许"信任该 planner 的同类图"一键通过？这会牺牲审核质量换吞吐，需要你定。
3. **两级拆解时，L1 是否也必须人审？** 我倾向必须——L1 就是架构决策，错误代价最高。但审批次数会翻倍。
4. **需求变更如何触发重拆？** 自动检测（需求 hash 变）还是人工点「重拆」？自动检测会误报，人工会漏报。

## 16. 一句话总结

**2.0 说"不要让平台调模型"，2.1 把它推到底：连拆解这个最像"平台该干的活"，也必须由一个终端去拉、去干、去交，人只对图签字。** 平台越像中转站，越活得久。
