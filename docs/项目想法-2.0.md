## 1. 定位（收敛为一句话）

**OpenVow 是一个私有工程场景的任务中台：人来定契约，终端来干活，平台只做派发、校验、归集。**

三个不可让渡的边界：

| 边界 | 含义 | 为什么不能让 |
| --- | --- | --- |
| 不持有模型凭证 | 平台不存任何模型服务商的 API Key / 账号 / Cookie | 这是「分散风控」的物理前提，也是法律上的责任边界 |
| 不主动调用 | 平台永不向模型发起请求，只回应终端 | 推模式会把风控重新集中回平台 |
| 不改写产物 | 平台只做校验与归档，不做内容修补 | 一旦允许改，Schema 契约就失去约束力 |

**注意用词修正**：1.0 说「平台不持有任何密钥」。这句要改成「不持有任何**模型服务商**凭证」。因为平台**必须**持有终端接入凭证（见第 6 节），否则任务池可被任意投毒。两种 Key 不是一回事，文档里必须区分清楚，否则后面实现时一定会打架。

## 2. 与 1.0 的差异（先看结论）

| # | 1.0 的说法 | 2.0 的修订 | 严重度 |
| --- | --- | --- | --- |
| 1 | 产物合规 = 产物可用 | 合规只是 L0–L2；新增**验收（acceptance）**作为 L3，通过才叫可用 | **致命** |
| 2 | pull + 认领回执是两个接口 | 合并为原子 `POST /claim`，返回即加租约；删除独立的「回执」 | 高 |
| 3 | 认领后「锁定」，超时释放 | 改为**租约（lease）+ 心跳续租 + 过期回收 + 重试计数** | 高 |
| 4 | 任务只声明输出 Schema | 新增 **`writes[]` 文件所有权声明**，冲突任务不得并行 | **致命** |
| 5 | 平台不持有任何密钥 | 改为「不持有模型凭证；持有终端接入凭证」 | 高 |
| 6 | 依赖「任务完成」即解锁 | 改为「任务 **accepted**」才解锁 | 中 |
| 7 | 底座选 Prefect / Jobd / NullBoiler | 见第 7 节：Prefect 与 pull 模式错配；NullBoiler 是推模式；M0 直接 Postgres `SKIP LOCKED` | 高 |
| 8 | 无密钥、匿名 ID 即可 | 增加 **base_revision** 与提交签名，防止旧基线产物静默覆盖 | 中 |
| 9 | 差异化 = 市场空白 | 收敛为「拉模式 + 代码工程契约 + 验收后可直接合并」的三元组合 | 中 |
| 10 | 匿名 ID 无映射 | 私有场景保留 terminal→owner 映射，匿名只存在于协议层 | 低 |

## 3. 评审清单（按严重度）

### P0-1 「Schema 合规」不等于「产物正确」

1.0 第五节整节都在讲怎么约束格式，但**从头到尾没有回答「怎么知道这个产物是对的」**。一个 Agent 完全可以交出目录结构完美、命名规范、JSON Schema 全过的代码，而里面是一堆 `pass` 和 `TODO`。

后果：平台的「零二次加工」承诺直接破产——因为你交付的是「格式正确的垃圾」，评审成本比没有平台还高。

修正：任务契约里必须带 `acceptance`，即**可执行的验收命令**：

```json
"acceptance": {
  "build": "cargo build --locked",
  "test": ["cargo test --locked", "cargo clippy -- -D warnings"],
  "expect_exit": 0,
  "timeout_s": 900,
  "evidence": "required"
}
```

平台校验分四层，每层是上一层的准入条件：

| 层 | 内容 | 谁执行 | 失败后果 |
| --- | --- | --- | --- |
| L0 结构 | 路径规范化、`writes[]` 越界、符号链接、大小上限 | 平台 | 直接 reject |
| L1 完整 | 哈希重算一致、`required_files` 齐全、编码/换行统一 | 平台 | reject |
| L2 形状 | `schema_output` 过 JSON Schema、linter 零 error | 平台 | reject |
| L3 行为 | `acceptance` 命令退出码符合预期 | 终端跑 + 平台抽检复跑 | `rejected`→重试 |
| L4 集成 | 按 DAG 顺序 apply 到主干后，全量构建/测试通过 | 平台（阶段 2 起） | `integration_failed` |

**只有 L3 通过，任务才进入 `accepted`。只有 L4 通过，才允许 `merged`。** 这是把「零二次加工」从口号变成可验证承诺的唯一办法。

### P0-2 「零二次加工」缺了文件所有权的物理前提

两个任务都改 `src/lib.rs`，各自都 100% 合规，合并必然冲突。1.0 完全没触碰这个问题。

修正：拆解阶段就给每个任务声明**写集**，平台在派发时做冲突检测：

```json
"writes": ["src/parser/**", "tests/test_parser.rs"],
"reads":  ["src/lib.rs", "docs/parser.md"]
```

规则：
- 两个 `queued/claimed` 任务的 `writes` 有交集 → **不得同时派发**（这是硬约束，不是优化）。
- 相对路径、`**` glob、只允许相对 workspace 根。
- 出现交集说明拆解错了，`POST /tasks/validate` 应提前报警，而不是等合并时炸。

这条规则会让「并行度」下降，但它是唯一能让「直接合并可用」成立的前提。**宁可少并行，不要假并行。**

### P1-1 pull 与 claim 之间的竞态

1.0 里「任务拉取」返回任务，「任务认领回执」再锁定。这中间是经典 TOCTOU：终端 A、B 同时拉到 T-0001，都能提交回执。

修正：删掉回执接口，`POST /claim` 一步完成「选任务 + 加锁 + 返回租约」。想「先看看有什么」的，用只读的 `GET /tasks/peek`（不改变任何状态，仅供看板/调试）。

### P1-2 「锁定」必须是有期限的租约

1.0 第十节提到「超时自动释放」，但协议里没有对应字段，等于没设计。

修正：认领返回 `lease_id` 与 `lease_expires_at`（默认 30 分钟）。终端每 5 分钟 `POST /heartbeat` 续租。过期由平台回收：

- `state: claimed → queued`，`attempts += 1`
- `attempts > max_attempts`（默认 2）→ `needs_human`，不再自动派发

没有租约的锁，在有终端随时失联的分布式环境里**必然死锁**。

### P1-3 「不持有任何密钥」与「防投毒」互斥

匿名 ID + `fingerprint_hash` 挡不住任何人往任务池里塞产物。私有工程场景下，这是不可接受的。

修正（三件事分开说）：

| 凭证 | 谁持有 | 用途 | 是否违反「分散风控」 |
| --- | --- | --- | --- |
| 模型 API Key | 只在终端 | 调模型 | 不涉及，平台永不见 |
| 终端接入 Token | 平台签发，终端持有 | 调 OpenVow 接口 | 不违反：这不是模型凭证 |
| 提交签名（HMAC/Ed25519） | 终端持有私钥 | 证明「哪个终端提交的」 | 不违反 |

另外：**私有场景不该真匿名**。协议层用 `agent_anon_id` 没问题，但平台侧必须保留 `terminal → owner → 项目` 的映射表。理由不是监控，而是质量治理——你需要知道「哪个终端连续产出垃圾」，否则多终端跑三个月后你没有任何手段收敛质量分布。

### P1-4 依赖用「完成」解锁，会把坏产物放进下游

`state: done` 只说明终端说了 success。必须改为 `accepted`（L3 通过）才解锁下游，否则下游会基于垃圾代码开工，返工成本指数级放大。

### P1-5 底座选型错配（重要更正）

我先纠正自己：`jobd` 与 `nullboiler` 是真实存在的项目（[jobd](https://github.com/musharna/jobd)、[nullboiler](https://github.com/nullclaw/nullboiler)），不是虚构的。但两个都不适合当 M0 底座：

- **NullBoiler** 的自我描述是「defines execution graphs, manages shared state, **dispatches work to agents**」——这是**推送型**编排器，和 OpenVow「终端主动拉取」的核心恰好相反。接它等于把平台变回推模式。
- **Jobd** 是 GPU-aware job broker，带 MCP 集成，方向比 NullBoiler 近，但项目极年轻、生态小，M0 引入它等于把最核心的状态机外包给一个 bus factor 很高的依赖。
- **Prefect** 是 Python 编排框架，push 调度 + 自己的执行器模型，要改成 pull 得逆着它的设计走。

**M0 推荐：Postgres + `FOR UPDATE SKIP LOCKED`，不引入任何队列中间件。**

```sql
-- 一次查询完成「原子认领」，天然无竞态
UPDATE tasks SET state = 'claimed',
       lease_id = $1, lease_until = now() + interval '30 minutes',
       terminal_id = $2, attempts = attempts + 1
WHERE id = (
  SELECT t.id FROM tasks t
  WHERE t.state = 'queued'
    AND t.schema_version = $3
    AND t.tech_stack && $4            -- 能力标签交集
    AND NOT EXISTS (                   -- 前驱未 accepted 的一律不给
      SELECT 1 FROM task_deps d JOIN tasks p ON p.id = d.parent_id
      WHERE d.child_id = t.id AND p.state <> 'accepted'
    )
  ORDER BY t.priority DESC, t.created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING *;
```

1.0 说「认领要加分布式锁」——不需要。`SKIP LOCKED` 就是这件事的标准解，单库、无 Redis、无锁服务。

### P2-1 产物覆盖旧基线，静默丢失别人的改动

提交必须带 `base_commit`（终端从哪个 commit 拉的）。平台记录；若主干已前进且 `writes` 有交集 → 标记 `stale`，要求 rebase 后重提交。没有这个字段，分布式并行迟早出「我的代码被谁删了」。

### P2-2 差异化叙述过强

1.0 第七节结论是「没有任何产品完全匹配」。严格说这是不可证伪的断言，而且 A2A 已经覆盖了任务生命周期与产物分段（[A2A tasks](https://docs.cloud.google.com/generative-ai-app-builder/docs/reference/rest/v1/projects.locations.collections.engines.assistants.agents.a2a.v1.tasks)）。

更站得住的表述：**「私有工程 + 代码契约 + 拉模式」这个三元组合，目前没有产品同时做全。** 单点都不新，组合是新的。投资人/合作方更容易买账，也不容易被一句「A2A 不就是这个吗」问死。

另外，「无内置 Agent」本身不是差异化——Airflow、Prefect 也没有内置 Agent。真正的差异化是「Agent 在平台之外、由别人付费、自己拉活」。

### P2-3 匿名 ID 与可追责的张力

见 P1-3。协议层匿名、平台层实名，两套视图。

## 4. 修订后的架构

```
┌──────────────────────────────────────────────────────┐
│ 控制面 Control Plane（人）                            │
│  需求拆解 · 契约定义(writes/acceptance/schema) · 看板  │
└───────────────────────┬──────────────────────────────┘
                        │ 写入任务与依赖
┌───────────────────────▼──────────────────────────────┐
│ 调度面 Scheduler（OpenVow 核心，无模型、无 Agent）      │
│  claim(原子+租约) · heartbeat · 冲突检测 · DAG 解锁     │
│  校验 L0–L3 · 事件日志 · 终端准入                       │
└──────┬────────────────────────────────┬──────────────┘
       │ 产物（内容寻址）                 │ 任务
┌──────▼──────────────┐        ┌────────▼──────────────┐
│ 产物库 Artifact      │        │ 执行面（平台外）        │
│  Store              │        │ Claude Code / DSH /   │
│ sha256 寻址·只读·    │◄───────┤ 自研 Agent            │
│ 不可变·可回溯        │ 上传    │ 自带账号、自带模型、    │
└─────────────────────┘        │ 自带风控               │
                               └───────────────────────┘
```

关键变化相对 1.0：

1. **产物库独立成一层**，内容寻址（sha256）、只读、不可变。1.0 里产物只是「结果里的 file_list」，那没法做审计和回溯。
2. **校验分四层**，L3 必须有执行证据，不能只信自报。
3. **执行面完全在平台外**，平台连它的进程都看不见——这是风控分散的物理保证。

## 5. 领域模型与状态机

### 5.1 任务状态

```
                    ┌─────────────┐
     拆解入库 ─────► │   draft     │
                    └──────┬──────┘
                           │ publish（校验 writes 不冲突、依赖存在）
                    ┌──────▼──────┐
              ┌─────┤   queued    │◄──────────────┐
              │     └──────┬──────┘               │
              │            │ claim（原子+租约）     │ lease 过期/放弃
              │     ┌──────▼──────┐               │
              │     │  claimed    │───────────────┘
              │     └──────┬──────┘
              │            │ submit
              │     ┌──────▼──────┐
              │     │ validating  │  L0–L2
              │     └──┬───────┬──┘
              │  pass  │       │ fail
              │  ┌─────▼──┐ ┌──▼────────┐
              │  │submitted│ │ rejected  │──► 重试或 needs_human
              │  └────┬───┘ └───────────┘
              │       │ L3 acceptance 通过
              │  ┌────▼─────┐
              └──┤ accepted │  ← 只有这个状态解锁下游
                 └────┬─────┘
                      │ L4 集成通过
                 ┌────▼─────┐
                 │  merged  │
                 └──────────┘
```

终态也叫 `needs_human`：自动流程放弃，等人介入。**不要设计「failed 就没了」**，工程上那意味着活丢了。

### 5.2 核心表（M0 用 SQLite 同构，字段一致）

```sql
terminals(id, token_hash, owner, labels jsonb, concurrency_limit,
          last_seen_at, banned_at)

tasks(id, project_id, summary, detail_doc_url, tech_stack jsonb,
      writes jsonb, reads jsonb, output_schema jsonb, schema_version,
      acceptance jsonb, priority, state, attempts, max_attempts,
      base_commit, created_at, deadline)

task_deps(parent_id, child_id)          -- child 依赖 parent

claims(id, task_id, terminal_id, lease_until, created_at)  -- 历史租约

artifacts(id, task_id, attempt, sha256, path, size, media_type,
          created_at)                    -- 内容寻址，行只存索引

events(id, task_id, kind, payload jsonb, at)  -- 审计日志，只追加

integrations(task_id, sequence, applied_commit, result)   -- L4
```

## 6. 协议 v1（三个必需 + 两个辅助）

原则不变：JSON over HTTPS、无敏感信息、极简。**所有写接口必须带 `Authorization: Bearer <terminal_token>`。**

### 6.1 `POST /v1/claim` — 原子认领（替代 1.0 的 pull + 回执）

```json
// 请求
{
  "agent_anon_id": "agent-0086",
  "labels": ["rust", "pyside6"],
  "max_concurrent": 1,
  "lease_seconds": 1800
}

// 200 有活
{
  "task_id": "T-20261021-0001",
  "lease_id": "L-7f3a...",
  "lease_expires_at": "2026-10-21T20:00:00Z",
  "summary": "...",
  "detail_doc_url": "...",
  "tech_stack": ["Rust", "PySide6"],
  "writes": ["src/**"],
  "base_commit": "9c1f...",
  "output_schema": { "$ref": "schema://code-module/v1" },
  "acceptance": { "build": "cargo build --locked", "test": ["cargo test"] },
  "deadline": "2026-10-22T12:00:00Z"
}

// 204 无活（不是 404，不要让终端把「没活」当错误重试）
```

### 6.2 `POST /v1/heartbeat`

```json
{ "task_id": "T-...", "lease_id": "L-7f3a...", "progress": "3/7 files" }
```

`409 lease_expired` → 终端必须立刻停手，不要再提交（否则会覆盖别人的 attempt）。

### 6.3 `POST /v1/submit`

```json
{
  "task_id": "T-...",
  "lease_id": "L-7f3a...",
  "attempt": 1,
  "base_commit": "9c1f...",
  "status": "success",
  "files": [{ "path": "src/demo.rs", "sha256": "..." }],
  "schema_output": {},
  "acceptance_evidence": {
    "build_exit": 0,
    "test_exit": 0,
    "log_snippet": "...",
    "duration_s": 214
  }
}
```

- `files` 只给路径与哈希，**二进制走 `PUT /v1/artifacts/{sha256}`**（先传后提交，可断点续传、天然去重）。
- 平台**重算**每个文件的 sha256，不信自报（1.0 第十节已提到，这里落到协议）。
- `status: success` 是**声明**，不是结论；结论由 L2/L3 给出。

### 6.4 辅助接口

- `GET /v1/tasks/peek?n=5` — 只看不拿，给看板和调试（不改变状态）。
- `POST /v1/tasks/validate` — 拆解侧预检：写集冲突、依赖成环、`acceptance` 可执行性。

### 6.5 错误码（定型，避免每个终端各写一套）

| 码 | HTTP | 含义 | 终端应做 |
| --- | --- | --- | --- |
| `lease_expired` | 409 | 租约已回收 | 停手，丢弃本地工作 |
| `write_conflict` | 409 | 写集与在途任务冲突 | 换任务 |
| `deps_unmet` | 409 | 前驱未 accepted | 换任务 |
| `schema_invalid` | 422 | L0–L2 失败（带 `violations[]`） | 修正后重提，计入 attempts |
| `acceptance_failed` | 422 | L3 失败 | 同上，但**不要重试同一方案** |
| `rate_limited` | 429 | 终端并发/频率超限 | 退避 |

## 7. 产物契约体系（2.0 的核心资产）

1.0 第五节列的是「约束项清单」，那是给人看的。2.0 要把它变成**机器可执行的四段式**：

```json
{
  "contract_version": "code-module/v1",
  "writes": ["src/parser/**"],
  "required_files": ["src/parser/mod.rs", "tests/test_parser.rs"],
  "style": { "linter": "clippy", "max_line": 100, "forbid": ["unwrap()"] },
  "schema_output": { "$ref": "schema://module-meta/v1" },
  "acceptance": { "build": "...", "test": ["..."], "timeout_s": 900 }
}
```

拆分原则（这条比 Schema 本身更重要，也是最容易失败的地方）：

- **单任务 ≤ 4 个文件、≤ 400 行 diff**。超过就该再拆。
- **单任务必须有独立的 `acceptance`**。写不出验收命令 = 这个任务没定义清楚，不许入库。
- **写集尽量不相交**。相交就是串行，接受它。
- **Schema 先极简**（1.0 第十节的判断是对的）：v1 只校验路径、必填文件、构建/测试退出码。等你跑满 50 个任务，再根据真实失败模式加约束。一上来写 30 条规范，Agent 只会全部糊弄过去。

文档类任务同构，只是 `acceptance` 换成「必填章节存在 + 链接可达 + 字数下界」，用脚本校验，不用模型。

## 8. 鉴权与信任模型

```
终端首次接入：管理员发放 token（一次性），终端本地保存
每次请求：    Authorization: Bearer <token>
提交可选加固： X-Signature: Ed25519(sign(sha256(canonical_body)), privkey)
平台侧保留：  terminals.owner / project_id（私有场景，不做真匿名）
```

- Token 可吊销（`banned_at`），这是唯一能止血的手段。
- 不在协议里传任何模型凭证——这条要写进终端接入检查清单，并在 `GET /v1/contract` 里返回「本平台永不索取模型 Key」的声明，让不放心的人自己验证。
- 不搞 OAuth、不搞多租户 RLS。M0 单项目，够用就行。

## 9. 技术选型（修订）

| 层 | 1.0 | 2.0 建议 | 理由 |
| --- | --- | --- | --- |
| 状态与队列 | Prefect / Jobd / NullBoiler | **Postgres**（M0 可 SQLite） | 认领就是一条 `SKIP LOCKED`；不引入中间件 |
| 锁 | Redis 分布式锁 | 不需要 | 行锁 + 租约已覆盖 |
| 产物存储 | 未提 | **本地目录（M0）→ MinIO/S3（M1）**，sha256 内容寻址 | 天然去重、可回溯、可审计 |
| 服务 | 未定 | 单二进制 HTTP 服务（Go 或 Python/FastAPI 二选一，见未决问题） | 3 个接口不值得上框架 |
| 前端 | 「简单后台」 | M0 用 CLI + `peek` 返回的 JSON；M2 再上 Web | 先别写看板，它是拖延症的温床 |
| 沙箱 | 未提 | L3 复跑用容器（Docker），限制网络与 CPU | 终端提交的代码不可信，复跑必须隔离 |

**明确不选**：Celery（Python-only、推模式）、Airflow（重型、DAG 静态）、Temporal（能力过剩，M0 用不上，但 L4 长事务阶段可考虑）。

## 10. MVP 阶段（带验收标准）

1.0 的四阶段方向对，但缺「怎么算过」。补上：

**M0 · 单机闭环（1–2 周）**
范围：单任务、无 DAG、单终端、CLI 操作。
验收：① 10 个终端并发抢 1 个任务，0 重复认领；② `kill -9` 终端后 60s 内任务回 `queued`，attempts 已 +1；③ 提交一个 `acceptance` 必失败的任务，状态必须停在 `rejected` 而非 `accepted`。

**M1 · 契约与依赖（2–3 周）**
范围：DAG、L3 验收、失败重试、产物库、写集冲突检测。
验收：① 三任务链 A→B→C，B 失败两次后 C 永不派发；② 两个写集相交的任务永不同时 `claimed`；③ 任一产物可按 sha256 回溯到 terminal + 时间 + attempt。

**M2 · 多终端治理（2 周）**
范围：标签匹配、并发上限、看板、token 吊销。
验收：① 一台终端刷接口被 429 限住；② 吊销 token 后 1 个请求内失效；③ 看板能看到「每终端 accepted 率」。

**M3 · 拆解辅助（按需）**
范围：辅助 Agent 生成拆解草案，人审后入库。
验收：生成 10 个任务草案，人只改 ≤ 30% 即可发布。

## 11. 风险清单（重排）

| 风险 | 1.0 判断 | 2.0 判断 |
| --- | --- | --- |
| **任务切分粒度** | 未列 | **第一大风险**。切太细→合并成本爆炸、上下文丢失；切太粗→并行度≈1。准则见第 7 节 |
| Schema 过复杂 | 已列，策略「先极简」 | 同意，且**必须**配套「写不出 acceptance 就不许入库」 |
| 认领冲突 | 「加分布式锁」 | 已解决：`SKIP LOCKED` + 租约 |
| 终端失联 | 「超时释放」 | 已解决：租约 + 心跳 + `needs_human` |
| 哈希绕过 | 「平台重算」 | 已解决：L1 + 内容寻址 |
| 终端风控 | 「终端内置限速」 | 保留；但注意**平台侧 429 不能替代终端侧限速**，两者互补 |
| **Agent 谎报成功** | 未列 | 新增：只信 L3 证据，不信 `status` |
| **产物基于旧基线** | 未列 | 新增：`base_commit` + `stale` 标记 |
| **平台无验收能力** | 未列 | 新增：L3 复跑必须容器隔离，否则等于在自己机器上跑陌生代码 |
| **成本不透明** | 未列 | 新增：分布式只省「封号」，不省「钱」。看板要统计每任务 token 消耗（终端自报），否则无法判断值不值 |
| **质量不可收敛** | 未列 | 新增：per-terminal accepted 率，低到阈值自动降权 |

## 12. 未决问题（需要你拍板）

1. **服务端语言**：Go 单二进制（部署最省事）还是 Python/FastAPI（生态、脚本化拆解方便）？这个决定会锁死后面所有实现。
2. **终端接入形态**：只出 HTTP 协议 + 一段 System Prompt（终端自己写循环），还是同时提供一个官方 `openvow-agent` CLI/SDK 来封装 claim/heartbeat/submit？后者体验好得多，但等于把「终端逻辑」也纳入了维护面。
3. **是否需要「人类审批」环节**：L3 通过就自动 `accepted`，还是加一道人工抽检？分布式场景下人工审批会成为瓶颈，但完全自动又可能放进「测试通过但架构错」的产物。
4. **M0 是否真的只对接一个 Harness**：建议先只对接 DSH（你当前环境就是），跑满 20 个真实任务再谈第二个。多 Harness 是 M2 的事，提前做会得到一堆抽象错误的适配层。
5. **产品边界**：这到底是自用工具、开源项目，还是要商业化？答案会改变「匿名 ID」「多租户」「计费」三块的设计重量——现在按自用最小实现，将来改起来是要动协议的。

## 附：一句话总结这次修订

1.0 解决的是「怎么把活分出去」，2.0 补的是「怎么保证分出去的活收回来是能用的」——**验收（L3）和文件所有权（writes）是这个平台真正的护城河，而不是协议本身。**
