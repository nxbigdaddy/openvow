分布式 Agent 任务分发与产物协同平台 设计概要
一、平台定位
不做内嵌多模型、多 Agent 的强耦合系统，以中立任务分发 + 标准协议层为核心，对接各类现成 Agent 执行终端（如 Claude Code、DeepSeek Harness、自研 Agent 等），实现大需求拆解、标准化任务派发、合规分布式执行、可直接复用的产物归集，同时规避集中式账号调用的风控与封号风险。
核心差异化定位：
无内置模型、无内置 Agent，纯中立任务中台
采用「终端主动拉取」而非平台主动推送，彻底分散风控风险
前置任务产物 Schema 契约，实现产物零二次加工、直接合并可用
二、核心整体架构
整套系统分为三层，极度松耦合、可分步落地：
上层：任务拆解与结构化管理层（人工 + 半自动）
负责人将大型软件工程、系统需求，拆解为无依赖弱耦合 / 带明确依赖的最小可执行子任务，每个任务绑定专属产物 Schema、技术栈约束、文件规范、输出契约。
中层：中立协议调度与状态中台（核心自研层）
提供统一 HTTP 协议接口、任务状态管理、任务认领防冲突、产物 Schema 校验、结果归集。不运行 AI 模型、不持有任何密钥。
下层：分布式异构 Agent 执行终端（第三方成熟组件）
任意支持自定义指令的 Code Harness、Agent 终端均可接入：DeepSeek Harness、Claude Code、OpenAI Kodex、自研通用 Agent 等。所有模型账号、调用行为、风控压力全部沉淀在终端。
三、完整核心业务流程
需求拆解入库
平台侧完成大型需求拆解，定义每个子任务：需求描述、技术栈、前置依赖、输出 Schema、文件规范、命名规则、截止条件，录入任务池。
终端主动轮询拉取任务
各在线 Agent 终端通过统一协议，主动请求可认领任务，平台根据标签匹配、任务状态、依赖完整性分发可执行任务。
终端认领锁定（防并发冲突）
任务被认领后平台自动锁定，避免多终端重复领取，任务状态变更为「执行中」。
终端本地独立执行
终端使用自身独立账号、独立模型环境完成代码生成 / 文档编写，不受平台管控，平台无任何调用行为，彻底规避集中风控。
按标准 Schema 产物输出
终端严格遵循任务绑定的 Schema 契约输出结果，文件结构、代码格式、字段结构、注释规范全部标准化。
标准化产物回传提交
终端通过协议提交完整产物、日志、哈希校验值。
平台自动校验与归集
平台校验产物合规性、完整性，无需人工二次修改、重构、整理，直接归档，可按需合并为完整工程。
任务闭环
任务标记完成，解锁依赖下游任务，形成自动化 DAG 流转。

五、产物 Schema 契约体系（平台核心价值）
1. 设计核心思想
任务拆解阶段即定死输出标准，从源头杜绝产物不可用、格式混乱、需要二次重构的问题。
平台不做内容修改，只做「合规校验 + 归集合并」。
2. 代码类任务通用 Schema 约束项
文件目录结构、文件名强制规则
模块导入规范、依赖版本约束
函数 / 类命名规范、注释规范
入参、出参、返回值固定结构
单元测试输出要求
错误处理范式
可直接合并到主工程的代码结构
3. 文档类任务 Schema 约束项
Markdown 固定标题层级
必填章节、字段
图文结构、排版规范
输出模板固定
六、风控与合规核心优势
完全分布式账号隔离
平台不持有任何 API Key、账号、令牌。所有模型调用、风控风险、限流风险全部由终端独立承担。彻底解决 Astropi Cloud、各类模型批量调用封号问题。
自然人化执行节奏
单终端单任务领取，无批量刷屏请求，规避平台风控特征。
责任边界清晰
平台仅做任务分发、协议中转、结果归集，不参与任何模型调用，无代调用、账号共享合规风险。
七、市面现有产品现状与差异化分析
结论前置
目前开源 / 商业圈内，没有任何一款成品完全匹配本平台的设计形态与核心诉求。
现有产品均只实现部分能力，核心逻辑与你的架构完全相反。
1. 传统任务调度框架（Airflow、Prefect、Celery）
优点：成熟的任务队列、状态流转、DAG 依赖、重试机制
致命差异：
面向程序 Worker 调度，不支持 Claude Code/Harness 这类 AI 终端主动接入
无 AI 产物 Schema 契约、无代码标准化输出约束
无法解决模型账号分布式风控问题
2. 主流 Agent 编排框架（AutoGen、CrewAI、LangGraph）
优点：支持多 Agent 分工、任务拆解、流程编排
致命差异：
推模式架构：平台主动调用 Agent、集中消耗 Token、集中风控，极易封号
强耦合模型，无法独立外置异构终端
无标准化产物 Schema，结果混乱、无法直接合并
3. 开放 Agent 集市协议（A2A、AgentHansa）
优点：支持 Agent 之间任务发布与认领
致命差异：
面向公共陌生人 Agent 网络，带激励、交易、信誉体系，不适合私有工程开发
无代码工程专属 Schema，无法产出可编译、可合并的工程代码
接入现有 Code Harness 改造成本极高
4. 商业低代码 Agent 平台（Dify、Coze、Hypertask）
优点：可视化任务、简单任务派发
致命差异：
强制绑定平台模型，无法隔离终端账号
产物无强 Schema 约束，不支持大型软件工程拆解开发
不支持异构 Harness / 自研 Agent 自由插拔接入
5. 市场空白总结
行业现有所有产品只有两种逻辑：
逻辑 A：平台集权，主动派活、主动调用模型（集中风控、产物不可控）
逻辑 B：公共开放 Agent 交易集市（不适合私有工程、无代码契约）
你的架构是行业空白形态：私有工程专属、前置 Schema 契约、终端主动拉取、分布式风控、零产物二次加工。
八、技术底座选型方案（快速落地、不重复造轮子）
最优落地策略：成熟调度底座 + 自研上层契约协议层
底层任务队列 & 状态底座
选用轻量自托管队列：Jobd / NullBoiler / Prefect
复用：任务持久化、状态流转、DAG 依赖、重试、锁机制，不自己从零写队列。
自研层（核心）
产物 Schema 定义与 JSON Schema 校验器
对外 HTTP 接口（拉取 / 认领 / 提交）
简单后台：录入任务、查看状态、查看产物、依赖编辑
终端接入侧
给每一类 Harness 一段固定 System Prompt，指导它按这套协议拉取任务、遵守 Schema、回传结果。
九、MVP 落地顺序（分阶段）
阶段 1：最小闭环验证
仅支持单任务，无复杂 DAG 依赖；实现拉取 → 认领锁定 → 提交 + Schema 校验。先对接一个 Code Harness 跑通。
阶段 2：增强任务能力
增加前置依赖 DAG、失败重试、产物文件存储、日志持久化。
阶段 3：多终端管理
终端标签匹配、并发限流、简单看板统计。
阶段 4：半自动拆解辅助
增加辅助 Agent，协助人把大需求拆成子任务（拆解仍然以人为最终审核）。
十、风险清单
Schema 写得太复杂，Agent 难以严格遵守；策略：先极简 Schema，逐步增加约束
多终端同时抢同一个任务；策略：任务认领加分布式锁，认领成功才锁定
终端失联、任务卡死；策略：增加超时自动释放机制
产物哈希校验绕过；策略：文件落地后平台侧重新计算校验值
终端侧风控：即使分散账号，短时间高频任务依然会触发模型服务商风控；策略：终端内置间隔限速
