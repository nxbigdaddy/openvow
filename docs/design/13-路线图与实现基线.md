## 15. 路线图

### M0 · 单终端闭环（1–2 周）

范围：手工建任务、CLI、单终端、无图、无并行。类型 `interface → test → implement` 手工串。

验收：

1. 三个任务串起来，最后一个 `accepted`；
2. 终端改冻结测试 → `frozen_file_modified`；
3. 空洞测试 → 红测试验收失败；
4. 越界写文件 → `path_outside_writes`；
5. 产物可按 sha256 回溯到 terminal + 时间 + attempt。

> **M0 不并行，但它已经是完整的产品**：契约 + 验收 + 冻结 + 归集。后面所有东西都是在它之上加并发。

### M1 · 图与契约（2–3 周）

`decompose` + planner + V1–V8 + 人审。验收：5 节点图能过校验并派发；写集冲突、接口缺失、类型拓扑错误各能被拦；驳回后 planner 能带 reason 重拆。

### M2 · 并行与信任（2 周）

多终端、写集互斥 SQL、租约/心跳/检查点、信任分、token 吊销。验收：10 终端并发 10 任务，0 重复、0 写集相交；`kill -9` 后 60s 内回队列且 attempts+1；检查点可续跑。

### M3 · 集成与修复（2–3 周）

集成任务自动物化、容器全量验证、失败包、repair 环路、canonical 合并。验收：故意造语义冲突 → 集成失败 → 自动 repair → 修复后合并；连续 3 次失败升级 `needs_human`。

### M4 · 规模化（按需）

两级拆解、merge group 分片、看板、许可证扫描、成本统计。

## 16. 实现基线（M0）

本节是 §15 中 M0 的实现约定；逐行细节见《M0 施工清单》。

### 16.1 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Go 1.22+ | 单二进制、标准库路由、无 CGO 依赖 |
| 存储 | SQLite（modernc，纯 Go） | 单文件、免安装；M2 迁 Postgres 时语义不变 |
| 路由 | `net/http` | 6 个端点不值得上框架 |
| 哈希 | `crypto/sha256` | 内容寻址 |

### 16.2 提交处理流水线

```
submit
  ├─ 0. 幂等：submissions(task_id, attempt) 已存在 → 返回上次结果
  ├─ 1. 租约：lease_id 匹配 且未过期
  ├─ 2. L0：路径规范化、⊆ writes、大小上限
  ├─ 3. L1：重算 sha256、冻结文件未被改动
  ├─ 4. 落盘：复制 repo → 用冻结版本覆盖 → 应用提交文件
  ├─ 5. L3：按 acceptance.kind 执行 build / run
  └─ 6. 写事件、更新状态
```

**第 4 步是防作弊的核心**：不管终端交了什么测试，一律用 `frozen` 的版本覆盖，再跑验收。

### 16.3 CLI

```bash
openvow serve --db ./openvow.db --repo ./demo --addr 127.0.0.1:7711
openvow terminal add --name t1 --out ./t1.token
openvow task new --kind test --title "解析器测试" --after T-0001 \
  --writes "src/parser/parser_test.go" \
  --acceptance '{"kind":"red_tests","build":"go test -run XXX ./parser","run":"go test ./parser"}'
openvow claim
openvow submit --dir .
```

`--after` 自动继承前驱 id 与冻结文件哈希，这是 M0 最关键的便利。

### 16.4 安全提醒

M0 在宿主机上执行 `acceptance` 命令，等于执行终端提交的代码。**只在你信任的仓库与终端上运行**，不要部署到共享环境。容器化是 M3 的事。
