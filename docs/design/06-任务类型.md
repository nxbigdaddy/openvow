## 7.1 七种类型

| kind | 目的 | 写集 | 验收 | 依赖 | 产物 |
| --- | --- | --- | --- | --- | --- |
| `decompose` | 需求 → 图 | ∅ | `graph_valid` | 无 | `task_graph.json` |
| `explore` | 调研 / 选型 / 原型 | 探索目录（禁源码） | `human_review` | 无 | 决策草案 + 证据 |
| `interface` | 冻结接口骨架 | 接口文件（独占） | `skeleton_build` | decompose 批准 | 骨架 + 签名清单 |
| `test` | 产出验收测试 | 测试 + fixtures | `red_tests` | interface | 测试源码 + 红证据 |
| `implement` | 实现功能 | 实现文件 | `green_tests` | test | 实现源码 |
| `integration` | 合并 + 全量验证 | 全仓（受控） | `full` | 组内全 accepted | 合并 commit + 报告 |
| `repair` | 修集成失败 | 冲突相关文件 | `full` | integration failed | 修复 diff |

## 7.2 `interface`：接口前置，独占，只读

**问题**：两个并行任务各自发明一套 API，各自用 stub 自测通过，合并时对不上。

**做法**：

- 每个模块至少一个 `interface` 任务，产出**可编译的骨架**：
  - Rust `pub fn parse(s: &str) -> Expr { todo!() }`
  - TypeScript `export function parse(s: string): Expr { throw new Error("not implemented") }`
  - Python `def parse(s: str) -> Expr: raise NotImplementedError`
  - 以及 `.proto` / `.d.ts` / `trait` / `interface` 定义。
- 骨架必须编译通过，否则下游测试写不出来。
- 该任务 `writes` 即接口文件集合；`accepted` 后，这些路径**全图只读**：
  - 后续任务 `writes` 命中 → V2 拒绝；
  - 提交命中 → L0 拒绝；
  - 要改 → 走图修订（新 interface 版本），下游标 `stale`。
- 产出 `openvow.interface.json` 签名清单，由语言提取器生成，不让模型手写。

**验收** `skeleton_build`：只要求构建通过，不跑逻辑测试（骨架里全是 `todo!()`，跑了必然 panic）。

**为什么必须先做**：它把"接口长什么样"从隐式约定变成显式产物。没有它，`decisions[]` 只能覆盖人想到的部分，剩余分歧全部堆到集成阶段爆炸。

## 7.3 `test`：独立任务，红测试验收

**问题**：实现方自己写测试，只要把断言改软就能通关。

**做法**：

- 测试由独立任务产出，`depends_on` 指向 `interface`，`writes` 只含测试与 fixtures；
- 实现任务 `depends_on` 指向测试，且**测试文件不在实现写集里**；
- 平台复跑实现任务时，**用冻结的测试覆盖终端交上来的测试**。

**验收** `red_tests`：测试在骨架上**必须失败**。

```json
{
  "kind": "red_tests",
  "build": "cargo test --locked --no-run",
  "run": "cargo test --locked",
  "expect": "fail",
  "min_failing_ratio": 0.8,
  "timeout_s": 900
}
```

判定（全部满足）：

1. `build` 退出码 0 —— 测试能编译；
2. `run` 退出码非 0 —— 确有失败；
3. 失败用例 / 总数 ≥ 0.8 —— 不是"一个红灯、其余全绿"的假红；
4. 失败原因是断言或 `not implemented` panic，不是编译错误。

**为什么能防住空测试**：`assert!(true)` 在骨架上是通过的，于是第 2 条不成立、整单被拒。想让测试被接受，唯一的办法是写出针对未实现行为会失败的断言。

**局限**：它防"空洞测试"，防不住"测试写错了需求"。后者靠 V4 覆盖度 + 人工抽检。

## 7.4 `implement`

- `writes` = 实现文件；接口与测试文件不在其中；
- 验收 `green_tests`：冻结测试全绿 + lint 零 error；
- 提交若包含测试文件 → L1 拒绝 `frozen_file_modified`。

## 7.5 `integration`：合并是一次执行

- **谁创建**：平台自动物化，不由 planner 写进图。规则：merge group 成员全部 `accepted` 后生成。
- **写集**：组内所有节点写集并集 + 热文件。此时其它任务都已 accepted，不存在冲突。
- **并发**：全局串行（同一 canonical 分支同一时刻只允许一个），由 SQL 约束保证。
- **执行**：claim 的终端拿到 bundle（组内全部产物 + 顺序），在临时分支按 DAG 顺序 apply，得 `candidate_commit`，容器内全量构建 + 测试。
- **通过**：fast-forward 到主干，组内任务标 `merged`。
- **失败**：生成失败包，创建 `repair` 任务。

**验收** `full`：全量构建 + 全量测试，超时 3600s。

**为什么由终端跑**：合并可能需要解决语义冲突（两个任务都对，组合起来类型不匹配），不是机械操作。平台只负责"按序应用 + 跑测试"。

## 7.6 `repair`

- 由集成失败触发，输入是失败包：`candidate_commit`、失败测试名、日志片段、相关 diff。
- `writes`：默认 = 失败测试覆盖到的文件；无法定位时放开到整个 group。
- 终端选择：优先派给**没有参与产出这些文件**的终端（避免作者盲区）。
- `accepted` 后，integration 以新 attempt 重跑；最多 3 次，超过 → `needs_human`。

## 7.7 `decompose`

- 输入：需求条目、`base_commit`、`decisions[]`、历史图的正/负样本；
- 输出：`task_graph.json`（只输出这个）；
- 验收 `graph_valid`：V1–V8 全过；
- 图不占任务池，未批准前执行终端不可见。

## 7.8 拓扑约束（V8）

```
explore ─┐
         ├──► interface ──► test ──► implement ──► integration ──► merged
decompose┘                                           │
                                                     └──► repair ──► integration
```

- 任何 `implement` 的祖先链上必须有 `interface` 与 `test`；
- `test` 的依赖必须指向 `interface`；
- `integration` 不进图（平台生成），图里出现即报错；
- 同一模块必须有且只有一个 `interface`；
- `explore` 若存在，必须是 `interface` 的祖先；
- `implement` 不得直接依赖 `explore`——必须经由 `interface` 把探索结果收敛成契约。

## 7.9 `explore`：探索性工作

**问题**：真实项目开头约两成时间花在"先调研、试做、再定方案"上。这类工作写不出可执行的 `acceptance`，也不该有源码 `writes`。没有这个类型，用户第一次遇到就会卡在"图建不出来"。

**做法**：

- 写集限定在探索目录（默认 `docs/explore/**`），**不得触碰源码**；
- 产出三件套：`options[]`（至少两个方案，各写代价）、`recommendation`、`evidence`（做过的实验、查过的资料、原型数据）；
- `acceptance.kind = human_review`：由人判定，平台只校验结构（三件套齐全、方案数 ≥ 2、无源码改动）；
- 不直接产出 `decisions[]`，只产出**决策草案**。人批准时决定是否采纳进图的下一版本。

**为什么不让它直接写 decisions**：架构决策权必须留在人手里（§2.4）。`explore` 的价值是让调研变成可追踪的产物，而不是把决策外包给模型。

**依赖**：可被 `interface` 依赖；`implement` 不得直接依赖 `explore`。
