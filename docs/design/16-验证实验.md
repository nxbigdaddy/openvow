> 原则：**不要做"能证明设计对"的实验，要做"能证伪设计"的实验。** 红线事先写好，结果出来只对照，不改标准。

## 20.1 六个生命体征

整套设计是否成立，最后会收敛到六个数字上。

| 代号 | 名称 | 定义 | 红线 |
| --- | --- | --- | --- |
| **P** | 并行度 | 按写集冲突 + 依赖做调度模拟，最大在途任务数的平均值 | ≥ 3 |
| **R** | 可验收率 | 能写出「基线红 / 实现绿」测试的任务数 ÷ 总任务数 | ≥ 0.6 |
| **C** | 契约开销 | 走完整流程的墙钟 ÷ 一人直写的墙钟 | ≤ 1.5 |
| **S** | 语义冲突率 | 并行模块合并时出现编译 / 测试失败的比例 | ≤ 0.2 |
| **T** | 评审吞吐 | 每天能审完的任务数 | ≥ 生产速度 × 0.5 |
| **V** | 变更税 | 需求变更导致重做的工时 ÷ 总工时 | ≤ 0.2 |

后续每一个实验，都是为了拿到其中一个数字。

## 20.2 第一梯队：半天，决定生死

### 实验 A｜可切分 + 可验收

一次拿 **P** 和 **R**，成本最低、决定力最大。

**材料**：三个真实需求，不用 demo 仓库——①一个新增功能（行为明确）；②一次存量改造（要动老代码）；③一组 bug 修复（5–10 个相关缺陷）。

**做法**：

1. 每个需求切成任务，记录 `writes` 与 `depends_on`；
2. **换一个人**（或另一个模型）逐任务判断：能不能写出「在基线上失败、在正确实现上通过」的测试；
3. 用这 9 张图跑调度模拟（按 `writes` 相交 + 依赖），算 P；
4. 统计 R。

**产出**：每个需求的 P 与 R，一张表。

**红线**：三个需求里有两个 P < 2，或平均 R < 0.5。

**不成立时**：P 低 → 收窄到"新增模块"场景，或在流程前加一个 `refactor` 任务先把存量改造成可并行形态；R 低 → 增加"人审验收"任务类型，把不可验收的工作显式排除，而不是假装它们有验收。

**纪律**：切分的人和验证的人不能是同一个。自己切自己验，一定得到"看起来都能切"的结论。

### 实验 B｜热文件分布

**材料**：三个真实仓库。

**做法**：对每个仓库问「新增一个模块，要动几个既有文件？」（注册表、`mod.rs`、路由、依赖清单），取中位数。

**产出**：热文件中位数。

**红线**：中位数 > 2。

**不成立时**：把"消除热文件"变成接入前置条件——这是一次性成本，但会改变项目结构，需要先说服人。

## 20.3 第二梯队：一周，决定机制

### 实验 C｜契约开销比

**材料**：一个中等模块（200–400 行）。

**做法**：同一模块走两条路——路径 a：一个人直接写并跑通测试；路径 b：`interface → test → implement → integration` 完整流程。记录墙钟、token、返工次数、最终代码可读性（找没参与的人盲评）。

**产出**：C = b 墙钟 ÷ a 墙钟。

**红线**：C > 1.5 且返工率未降到 50% 以下。

**不成立时**：把 `interface` 与 `test` 合并成一个任务（一次产出骨架 + 测试），或用模块级模板复用契约，压低边际成本。

**这一条最关键**：它直接检验"用三成前置成本换掉集成返工"这个核心交易。若 C 是 2.5，那不是设计问题，是假设错了。

### 实验 D｜红测试可行性

**做法**：给 10 个任务写测试，只允许"在骨架上必须失败"的写法。统计：①一次通过 `red_tests` 的比例；②**假红灯率**——抽样做变异测试（把骨架里某个函数改成返回错误值，看测试能否抓住）。

**产出**：两个比例。

**红线**：假红灯率 > 20%。

**不成立时**：退回"冻结测试 + 人写测试"模式（成本高但可靠），或把变异测试作为集成前的抽样手段。

### 实验 E｜语义冲突

**材料**：两个"文件不相交但接口相关"的模块（如解析器与求值器）。

**做法**：两个终端并行实现，各自跑通自己的测试后合并。记录是否编译失败、是否测试失败、原因是"接口对不上"还是"行为不一致"。重复 5 组。

**产出**：S。

**红线**：S > 0.2。

**不成立时**：在 `test` 任务里增加"跨模块契约测试"（调用方写的、针对接口的测试），把语义不一致前移到任务内。

## 20.4 第三梯队：随真实使用产生

### 实验 F｜信任分对抗

**做法**：写一个"恶意终端"脚本：先接 20 个小任务全过（刷 trust 到 0.95），第 21 个提交"测试被改软但哈希伪造"的产物，看抽检能否抓住。

**产出**：抓住率。

**红线**：抓不住。

**不成立时**：改按任务风险加权抽检——大 diff、改接口、碰热文件的永远 100% 复跑，与 trust 无关。

### 实验 G｜评审吞吐

**做法**：记录每次审图、审产物的实际分钟数。

**产出**：T。

**红线**：T < 生产速度的一半。

**不成立时**：加背压阀（未评审的 accepted 任务超过 N 个时整体降优先级），同时提高自动验收覆盖比例。

### 实验 H｜变更税

**做法**：记录真实项目里需求变更次数、每次牵连任务数、重做工时。

**产出**：V。

**红线**：V > 0.2。

**不成立时**：只接"需求稳定"的项目，或把变更窗口前移（图批准后 24 小时内允许免费改）。

### 实验 I｜反向基准

**做法**：同一模块，一次让当前最强模型整包做完，一次走完整流程，比总成本（token + 人时）。

**产出**：成本比。

**意义**：这条不是看现在，是看趋势。若整包做已经接近，这套设计的时间窗口就在关闭——那时它的价值应收缩到"审计与协作"，而不是"并行"。

## 20.5 实验纪律

1. **材料必须真实。** 用自己写的 demo 仓库做实验，结论一定是"很适合切分"——因为你就是照着设计写的。
2. **红线先写。** 看完数据再定标准，等于没有标准。
3. **记录失败原因，不只记录成功。** 每次切分失败、每次红测试写不出来，都是设计约束的真实来源。
4. **三类需求都要**：新功能、存量改造、bug 群。只在新增模块上成立，等于只覆盖三分之一的真实工作。
5. **不要优化实验。** 第一个实验的目的是拿到数字，不是做出一个好用的原型。

## 20.6 如果只做一个

**做实验 A + B，一个下午，得到 P 和 R。**

- P ≥ 3 且 R ≥ 0.6 → 继续做 M0，同时用实测值替换本文里那些拍脑袋的阈值；
- P < 2 → 收窄定位到"新增模块开发"，把存量改造明确排除；
- R < 0.5 → 承认"大部分工作没有可执行验收"，重新设计人审环节，别用红测试假装覆盖。

这两个数字一旦拿到，本文里六成的争论会自动消失——因为它们本来就是在争"这个前提成不成立"。

## 20.7 结果回写：实验替换哪些常量

实验的意义不是"验证一下"，而是**把假设换成数字**。下表说明每个数字应该回写到本文的哪一处。

| 实验 | 产出 | 回写位置 | 现在那里的值 |
| --- | --- | --- | --- |
| A | P | §14 R2、§15 M2 验收 | "并行度 < 2 告警"（拍的） |
| A | R | §9.2 L3 覆盖、§3.4 回本门槛 | 无覆盖率要求 |
| B | 热文件中位数 | §10.4 策略优先级、§3.2 scope guard | 无阈值 |
| C | C | §13 成本模型、§17 ADR-06/07 | "25–35% 前置成本"（估的） |
| D | 假红灯率 | §7.3 红测试判定 | `min_failing_ratio = 0.8`（拍的） |
| E | S | §7.3 跨模块契约测试 | 未设计 |
| F | 抓住率 | §10.3 信任分抽检 | 5% / 20% / 50%（拍的） |
| G | T | §10 背压（待补） | 无背压 |
| H | V | §3.4 回本门槛 | "每周 15 任务"（拍的） |
| I | 成本比 | §3.5 定位、§19.6(8) | 无数据 |

> 一条元规则：**任何没有实验来源的数字，在评审时都应被视为"待定"，而不是"已定"。**
