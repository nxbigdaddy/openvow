## 8.1 任务契约

```json
{
  "id": "N-03",
  "kind": "implement",
  "title": "解析器主流程",
  "summary": "基于 N-01 的骨架实现 parse / parse_expr",
  "writes": ["src/parser/impl/**"],
  "reads": ["src/parser/mod.rs", "src/parser/ast.rs", "tests/parser/**"],
  "provides": [],
  "consumes": ["parser::parse", "parser::Expr"],
  "depends_on": ["N-01", "N-02"],
  "covers": ["R-14/2.1", "R-14/2.2"],
  "acceptance": {
    "kind": "green_tests",
    "build": "cargo build --locked",
    "run": "cargo test --locked parser",
    "expect": "pass",
    "timeout_s": 900
  },
  "est": { "files": 3, "diff_lines": 320 }
}
```

| 字段 | 规则 |
| --- | --- |
| `writes` | 相对仓库根 glob；两任务相交 → 拒；命中冻结接口路径 → 拒 |
| `reads` | 只影响终端取上下文，不参与冲突判定 |
| `provides/consumes` | 见 §8.2 |
| `depends_on` | 只表达"必须等它 accepted" |
| `covers` | 必须引用需求条目 id；未覆盖会被 V4 点名 |
| `acceptance.kind` | `graph_valid` / `skeleton_build` / `red_tests` / `green_tests` / `full` |

## 8.2 接口契约

- `provides`：本任务承诺新增的符号（来自 `openvow.interface.json`）；
- `consumes`：本任务依赖的符号；
- **V7 闭合性**：每个 `consumes` 必须在同图某节点的 `provides` 里，或存在于 `base_commit` 的导出符号中。

**诚实说明**：V7 只做名字级匹配（符号存在 + 参数个数），不做完整类型检查。真正的类型一致性由 `green_tests` 的编译阶段兜底——这正是测试必须先写的原因。

## 8.3 验收冻结

| 冻结对象 | 何时冻结 | 怎么强制 |
| --- | --- | --- |
| 接口文件 | `interface` accepted | 全图只读；提交命中即 L0 拒 |
| 测试文件 | `test` accepted（记 sha256） | 复跑用冻结版本覆盖；提交版本不同 → `frozen_file_modified` |
| 验收命令 | 图批准 | 任务不能改自己的 `acceptance` |

推论：**实现方永远无法给自己判卷。** 它能改的只有实现文件，判卷的是别人写的、被平台冻结的测试。

## 8.4 图契约

```json
{
  "schema": "openvow/graph/v2",
  "requirement": {
    "id": "R-14",
    "title": "表达式解析器",
    "items": [
      { "id": "R-14/2.1", "text": "支持四则运算与括号" },
      { "id": "R-14/2.2", "text": "错误输入返回带位置的 ParseError" }
    ],
    "base_commit": "9c1f3ab"
  },
  "decisions": [
    { "id": "D-1", "text": "手写递归下降，不引入生成器", "affects": ["N-01"] }
  ],
  "nodes": ["…见 §8.1…"],
  "uncertain": ["需求未说明错误恢复策略"]
}
```

设计取舍：

- **不存 `edges`**：依赖只在 `depends_on`，边由它推导，避免两处漂移；
- **`decisions[]` 是人的领地**：planner 不得新增架构决策；
- **`uncertain[]` 是逃生口**：让 planner 承认不确定，比逼它编一个完整图好。
