## 5.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 控制面（人）                                                  │
│  需求条目化 · 图审批 · 契约修订 · 看板                          │
└───────────────────────────┬──────────────────────────────────┘
                            │ 获批的图 → 任务
┌───────────────────────────▼──────────────────────────────────┐
│ 调度面（平台：无模型、无 Agent、无模型 Key）                    │
│  claim（原子 + 写集互斥）· 租约 / 心跳 / 检查点                 │
│  DAG 解锁 · V1–V8 图校验 · L0–L3 产物校验 · 信任分抽检          │
│  准入 · 审计     ← 有状态的唯一真源                            │
└──────┬───────────────────────────────────────┬───────────────┘
       │ 产物（内容寻址）                        │ 工作区 / 主干
┌──────▼──────────────┐                ┌───────▼───────────────┐
│ 产物库 Artifact     │                │ canonical repo 镜像   │
│ sha256 · 只读 · 不可变│                │ 平台维护的唯一主干     │
└─────────────────────┘                └───────┬───────────────┘
                                               │
┌──────────────────────────────────────────────▼───────────────┐
│ 执行面（平台边界之外）                                        │

└──────────────────────────────────────────────────────────────┘
```

## 5.2 参与者

| 参与者 | 职责 | 凭证 |
| --- | --- | --- |
| 人 | 写需求条目、批准图、修订契约、处理 `needs_human` | human token |
| planner 终端 | 把需求拆成图 | terminal token（scope=planner） |
| 执行终端 | 领 interface / test / implement / integration / repair | terminal token（scope=worker） |
| 平台 | 派发、校验、归集、合并、审计 | 无模型凭证 |

## 5.3 一次完整循环

1. 人把需求写成条目化文档（每条有稳定 id）。
2. 人发一个 `decompose` 任务。
3. planner 终端 claim，读需求 + 仓库快照 + `decisions[]`，产出 `task_graph.json` 草案。
4. 平台跑 V1–V8，把 `violations[]` 返回给 planner；不通过就改。
5. 人审 diff，局部改或驳回；通过后图 `active`。
6. 平台把图展开成任务，按拓扑排布；`integration` 由平台生成、置于末尾。
7. 各终端独立 claim。**同时被认领的任务写集两两不相交**。
8. 终端提交产物与证据；平台跑 L0–L3，通过则 `accepted`，解锁下游。
9. 一个 merge group 全部 `accepted` 后，`integration` 解锁。
10. 某终端 claim 集成，按 DAG 顺序 apply 到临时分支，容器内全量构建 + 测试。
11. 通过 → fast-forward 到主干，`merged`；失败 → 生成 `repair` 任务，回到第 7 步。
12. 全部 `merged` 后需求闭环；看板记录墙钟、成本、返工。

## 5.4 部署形态

| 形态 | 组成 | 适用 |
| --- | --- | --- |
| T0 单机 | 单二进制 + SQLite + 本地目录 | M0 / M1，单终端 |
| T1 服务化 | api + Postgres + 对象存储（MinIO/S3）+ 反向代理 | M2 起，多终端 |
| T2 隔离 | T1 + 独立 runner 主机 + 容器运行时 | M3 起，跑不可信构建 |

**平台自身永远不挂模型 SDK**，镜像里不应出现任何模型供应商的依赖——这是可以被审计的硬约束。

## 5.5 代码同步与 canonical repo

终端必须能看到别人已 `accepted` 的代码，否则每个任务都在对过期快照工作。

| 项 | 设计 |
| --- | --- |
| 镜像 | 平台维护 `projects(mirror_url, canonical_ref, head_commit)`，从 origin 单向拉取 |
| 认领 | `claim` 返回 `repo_url` 与 `base_commit`；终端自行 fetch 后 checkout |
| 提交 | 终端**不 push**，只交文件哈希；二进制走 artifact 上传 |
| 合并 | 只有集成任务能把产物写成 commit；平台只决定顺序，不改字节 |
| 回传 | 可选推回 origin，默认只留在平台主干 |
