# OpenVow M0 施工清单

> 本文是见 [13-路线图与实现基线.md](13-路线图与实现基线.md) §16「实现基线」的逐行细化版。
> **范围**：单终端、无图、无并行、手工串链。**目标**：两周内跑通一个"能判卷、判卷的人不是考生"的最小闭环。

---

## 1. M0 交付什么

一个 Go 单二进制 `openvow`，同时是**服务端**和**终端 CLI**；一个 SQLite 库；一个能验证五条验收标准的脚本。

跑通后你会得到：

```
openvow task new --kind interface ...   →  终端 claim  →  写骨架  →  submit  →  accepted
openvow task new --kind test --after T1 →  claim  →  写测试（必须在骨架上红）  →  accepted
openvow task new --kind implement --after T2 → claim → 实现  →  测试绿  →  accepted
```

**M0 不并行**，但它是完整产品：契约、冻结、判卷、归集、追溯全在。后面所有并发能力都是在它之上加。

---

## 2. 技术选型（定死）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | **Go 1.22+** | 单二进制、部署零依赖、标准库自带路由（`http.ServeMux` 的 method 模式） |
| 存储 | **SQLite**（`modernc.org/sqlite`，纯 Go 无 CGO） | 单文件、免安装；M2 迁移 Postgres 时字段语义不变 |
| 路由 | 标准库 `net/http` | 6 个端点不值得上框架 |
| 哈希 | `crypto/sha256` | 内容寻址 |
| 配置 | 环境变量 + 命令行 flag | 不上配置文件 |
| 测试 | 标准库 `testing` + `httptest` | 无第三方 |

**为什么不是 Python**：M0 的核心是"文件落盘 + 哈希 + 起进程跑命令 + 事务"，Go 在这四件事上都是标准库直出；Python 会引入虚拟环境、依赖锁定、启动器三个额外问题。如果团队只会 Python，替换成本主要在 §6 的四个 handler，表结构与验收语义完全不变。

**为什么不用 Postgres**：M0 没有并发认领，`SKIP LOCKED` 用不上。但 DDL 要写成能平滑迁移的样子（见 §4 的注释）。

## 4. 数据模型（M0 DDL）

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE terminals (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  token_hash  BLOB NOT NULL,          -- sha256(token)
  created_at  TEXT NOT NULL,
  banned_at   TEXT
);

CREATE TABLE tasks (
  id             TEXT PRIMARY KEY,
  kind           TEXT NOT NULL CHECK (kind IN ('interface','test','implement')),
  title          TEXT NOT NULL,
  summary        TEXT NOT NULL DEFAULT '',
  -- 迁移预留：M2 换成 Postgres text[]，语义不变
  writes_json    TEXT NOT NULL,       -- ["src/parser/**"]
  reads_json     TEXT NOT NULL,       -- ["src/parser/mod.go"]
  frozen_json    TEXT NOT NULL,       -- [{"path":"a.go","sha256":"…"}]
  acceptance_json TEXT NOT NULL,      -- 见 §5.2
  requires_json  TEXT NOT NULL,       -- ["T-0001"] 全部 accepted 才可 claim
  state          TEXT NOT NULL,       -- queued/claimed/validating/accepted/rejected/needs_human
  attempts       INTEGER NOT NULL DEFAULT 0,
  max_attempts   INTEGER NOT NULL DEFAULT 2,
  lease_id       TEXT,
  lease_until    TEXT,                -- RFC3339 UTC，服务端时钟
  terminal_id    TEXT REFERENCES terminals(id),
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL
);

CREATE TABLE artifacts (
  sha256     TEXT PRIMARY KEY,
  size       INTEGER NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE task_files (
  task_id  TEXT NOT NULL,
  attempt  INTEGER NOT NULL,
  path     TEXT NOT NULL,             -- 相对仓库根，已规范化
  sha256   TEXT NOT NULL REFERENCES artifacts(sha256),
  PRIMARY KEY (task_id, attempt, path)
);

CREATE TABLE submissions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id     TEXT NOT NULL,
  attempt     INTEGER NOT NULL,
  lease_id    TEXT NOT NULL,
  accepted    INTEGER NOT NULL,       -- 0/1
  code        TEXT,                   -- 拒绝原因码
  detail_json TEXT,                   -- violations / 日志摘要
  created_at  TEXT NOT NULL,
  UNIQUE (task_id, attempt)           -- 幂等键
);

CREATE TABLE events (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id      TEXT,
  kind         TEXT NOT NULL,         -- claim/heartbeat/submit/reject/expire
  payload_json TEXT,
  at           TEXT NOT NULL
);
```

**迁移注意**：`writes_json` 现在用 JSON 文本，因为 M0 不需要数组交叠运算。M2 换 Postgres 时改成 `text[]` 并加 GIN 索引，`&&` 才能用上。

## 5. 契约

### 5.1 任务创建参数

```bash
openvow task new \
  --kind implement \
  --title "解析器主流程" \
  --writes "src/parser/impl/**" \
  --reads "src/parser/mod.go,tests/parser/**" \
  --after T-0002 \
  --acceptance '{"kind":"green_tests","build":"go build ./...","run":"go test ./parser","timeout_s":300}'
```

`--after` 做三件事（这是 M0 最关键的便利）：

1. `requires` 追加该任务 id；
2. 若是 `implement` 且前置是 `test`：把该 test 任务**全部产物路径与哈希**写入 `frozen_json`；
3. 若是 `test` 且前置是 `interface`：把接口文件写入 `frozen_json`。

### 5.2 三种验收

```json
// interface
{"kind":"skeleton_build","build":"go build ./...","timeout_s":300}

// test（必须在骨架上红）
{"kind":"red_tests","build":"go test -run XXX ./parser","run":"go test ./parser",
 "expect":"fail","min_failing_ratio":0.8,"timeout_s":300}

// implement
{"kind":"green_tests","build":"go build ./...","run":"go test ./parser","timeout_s":300}
```

判定矩阵：

| kind | build | run | 结论 |
| --- | --- | --- | --- |
| `skeleton_build` | 0 | 不跑 | 0 → accepted |
| `red_tests` | 0 | ≠0 且失败率 ≥ 0.8 | accepted |
| `red_tests` | 0 | 0（全绿） | `tests_not_red` —— 这是空测试的信号 |
| `red_tests` | ≠0 | — | `build_failed` |
| `green_tests` | 0 | 0 | accepted |
| `green_tests` | 0 | ≠0 | `acceptance_failed` |

## 6. HTTP 端点（6 个）

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| POST | `/v1/claim` | `{"kinds":["implement"],"labels":["go"]}` | 200 任务 / 204 无活 |
| POST | `/v1/heartbeat` | `{"task_id":"…","lease_id":"…"}` | `{"remaining_seconds":n}` |
| POST | `/v1/submit` | 见下 | `{"accepted":bool,"code":"…","violations":[]}` |
| PUT | `/v1/artifacts/{sha256}` | 原始字节 | 204 |
| GET | `/v1/artifacts/{sha256}` | — | 原始字节 |
| GET | `/v1/tasks/peek?state=queued` | — | 任务列表 |

鉴权：`Authorization: Bearer <token>`，中间件换成 `terminal_id` 注入 context。

**submit 报文**：

```json
{
  "task_id": "T-0003",
  "lease_id": "L-7f3a",
  "attempt": 1,
  "files": [{"path": "src/parser/impl/mod.go", "sha256": "…"}],
  "evidence": {"exit_code": 0, "duration_s": 42, "log_snippet": "…"}
}
```

## 7. 提交处理流水线（核心逻辑，按顺序）

```
submit
  ├─ 0. 幂等：submissions(task_id, attempt) 已存在 → 直接返回上次结果
  ├─ 1. 租约：lease_id 匹配 且 lease_until > now，否则 409 lease_expired
  ├─ 2. L0 结构
  │    ├─ 路径规范化（拒绝 .. / 绝对路径 / 符号链接）
  │    ├─ 每个路径必须命中 writes 的某个 glob，否则 path_outside_writes
  │    └─ 单文件 ≤ 2MB，总计 ≤ 50MB
  ├─ 3. L1 完整
  │    ├─ 重算 sha256，与提交值比对
  │    ├─ 命中 frozen 且哈希不同 → frozen_file_modified
  │    └─ frozen 文件必须**未被提交**（提交了也算改）
  ├─ 4. 落盘 workspace
  │    ├─ 复制 repo 到临时目录
  │    ├─ 用 frozen 的版本覆盖（防止终端夹带）
  │    └─ 应用提交的文件
  ├─ 5. L3 行为：按 acceptance.kind 执行 build / run，带超时
  ├─ 6. 写事件、更新状态
  │    ├─ accepted：任务置 accepted，解锁下游
  │    └─ 其他：attempts+1；超限 → needs_human，否则回 queued
  └─ 返回
```

**第 4 步是防作弊的核心**：不管终端交了什么测试文件，一律用 `frozen_json` 里的版本覆盖。终端改测试 = 无效，且会被第 3 步判 `frozen_file_modified`。

## 8. CLI 命令

```bash
# 起服务（repo 是被拆解的目标工程目录）
openvow serve --db ./openvow.db --repo ./demo --addr 127.0.0.1:7711

# 终端注册（输出一次性的 token）
openvow terminal add --name t1 --out ./t1.token

# 建任务
openvow task new --kind interface --title "解析器骨架" --writes "src/parser/**" \
  --acceptance '{"kind":"skeleton_build","build":"go build ./..."}'
openvow task new --kind test --title "解析器测试" --after T-0001 \
  --writes "src/parser/parser_test.go" \
  --acceptance '{"kind":"red_tests","build":"go test -run XXX ./parser","run":"go test ./parser"}'
openvow task new --kind implement --title "解析器实现" --after T-0002 \
  --writes "src/parser/impl/**" \
  --acceptance '{"kind":"green_tests","build":"go build ./...","run":"go test ./parser"}'

# 查看
openvow task list
openvow task show T-0002

# 终端侧
export OPENVOW_TOKEN=$(cat t1.token)
openvow claim                     # 打印当前任务 + 契约 + frozen 列表
openvow submit --dir .            # 扫描 writes 命中的文件，算哈希，提交
openvow heartbeat --lease L-7f3a  # 长任务手动续租（M0 无自动心跳）
```

`openvow claim` 的输出要**直接可读**，因为 M0 的"适配器"就是人 + Claude Code：把人看到的这段贴进 CLI 会话，Agent 就知道该干什么、不许碰哪些文件。

## 9. 子任务分解（自己吃自己的狗粮）

| # | 任务 | 产出 | 验收 |
| --- | --- | --- | --- |
| S1 | 存储层 | `store` 包 + 迁移 + 种子数据 | 表能建、事务能回滚、`go test ./internal/store` 绿 |
| S2 | 契约层 | 路径规范化、glob 匹配、冻结比对 | 表格驱动的 20 个用例全绿（含 `..` 绕过、绝对路径、符号链接） |
| S3 | 提交流水线 | §7 的 6 步 | 6 个拒绝码各有单测，顺序正确（幂等先于租约） |
| S4 | HTTP + CLI | 6 端点 + 6 子命令 | `curl` 全覆盖；CLI 端到端能 claim→submit |
| S5 | 验收脚本 | `m0-acceptance.ps1` | 五条标准全过，输出可读报告 |

建议顺序：S1 → S2 → S3 → S4 → S5。S2 可以并行做（无依赖），但 M0 只有你一个人，串行更省心。

## 10. 五条验收标准（Definition of Done）

脚本一跑，输出五行 PASS/FAIL：

| # | 标准 | 验证方式 |
| --- | --- | --- |
| 1 | 三个任务串起来，最后一个 `accepted` | 串行 claim→submit 三次，断言最终状态 |
| 2 | 改冻结测试被拒 | 提交前改 `parser_test.go` 一个字节 → 期望 `frozen_file_modified` |
| 3 | 空测试被拒 | 测试写成 `func TestX(t *testing.T){}` → 骨架上全绿 → 期望 `tests_not_red` |
| 4 | 越界写被拒 | 提交 `src/main.go`（不在 writes 里）→ 期望 `path_outside_writes` |
| 5 | 产物可追溯 | `openvow task show T-3` 能列出每个文件的 sha、terminal、attempt、时间 |

**第 3 条是 M0 的灵魂。** 它证明"判卷的人不是考生"这条原则不是口号，而是能被执行器机械判定的。

## 13. M0 明确不做

| 不做 | 何时做 |
| --- | --- |
| 图（graph）、planner、人审 | M1 |
| 多终端、并行认领、写集互斥 SQL | M2 |
| 租约自动续期、检查点、断点续跑 | M2 |
| Postgres、`SKIP LOCKED` | M2 |
| 容器隔离（**M0 在当前机器上跑验收命令**） | M3 |
| 信任分、抽检 | M2 |
| integration / repair 任务 | M3 |
| `explore` 任务类型 | M1（M0 只做 interface/test/implement） |
| MCP 适配器 | M2（有了并行才需要） |

**安全提醒**：M0 在宿主机上执行 `acceptance` 命令，等于执行终端提交的代码。**只在你信任的仓库和终端上跑**，不要接入外部不可信来源。容器化是 M3 的事，在那之前别把它部署到共享环境。

## 14. 完成之后先做什么

1. 用一个**真实的小需求**（不是 demo）跑一遍：3–5 个任务，看返工发生在哪一步。
2. 把返工原因记下来——这些就是 M1 里 V 组校验的规则来源。
3. 如果真实需求跑下来返工率 > 40%，先别急着做 M1 的图，回头把**契约字段**改对（大概率是 `writes` 切得太粗或 `acceptance` 写得太虚）。

## 15. 一句话

**M0 只证明一件事：一个 Agent 交上来的东西，能不能被判卷——而判卷的人，不是它自己。**
这一条立住了，后面加多少并发都是工程问题；这一条立不住，加多少并发都是灾难。
