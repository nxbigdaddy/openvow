## 2. 概述

### 2.1 一句话

**OpenVow 是一个私有工程的任务中台：人定契约，终端干活，平台只做派发、校验、归集、合并。**

### 2.2 要解决的三个问题

| # | 问题 | 现状 |
| --- | --- | --- |
| P1 | 大需求只能串行做 | 一个 Agent 会话从头做到尾，墙钟时间等于全部工作量，且中途崩溃就从零重来 |
| P2 | 并行产出合不起来 | 多个 Agent 各自发明接口、各自写测试、各自用 stub 自测通过，合并时接口对不上、测试被改软 |
| P3 | 多账号调用被集中管控 | 一旦做成"平台调模型"，所有 Token、限流、封号风险都压回中心，且成本不可分摊 |

多数"多 Agent 编排"产品把 P1 当成唯一问题，用并行解决它，结果把 P2 放大成灾难：**产出的代码多了 5 倍，能合并的没有变多。**

### 2.3 解题思路

```
把「能不能并行」变成「契约能不能先冻结」
把「能不能合并」变成「判卷的人是不是考生」
把「谁在调模型」变成「终端自己调，平台永不见 Key」
```

对应三个机制：

1. **前置契约**：动手之前，接口、测试、验收命令全部冻结，产物不需要二次加工。
2. **独立判卷**：测试由独立任务产出、平台冻结执行，实现方无法给自己打分。
3. **合并即任务**：集成不是流水线上一个勾选步骤，而是一次真实的构建与测试执行，失败会生成修复任务。

### 2.4 五条设计原则

| # | 原则 | 推论 |
| --- | --- | --- |
| 1 | **平台不持有模型凭证** | 任何需要模型的动作，都必须由终端完成 |
| 2 | **平台不主动调用** | 只有终端拉取，没有平台推送 |
| 3 | **平台不改写产物** | 只做校验、归档、按序合并，不做修补 |
| 4 | **没有隐含动作，只有任务** | 拆解、写接口、写测试、写实现、合并、修复，都是任务 |
| 5 | **判卷的人不是考生** | 验收产物与实现产物必须来自不同任务，且前者被冻结 |

## 3. 范围与前提

### 3.1 做什么

- 把一个较大的软件需求，切成**文件不相交、接口已冻结、验收可执行**的子任务；
- 分发给多个自带模型账号的终端，并行执行；
- 对每个产物做结构性校验与行为验收；
- 把合格产物按 DAG 顺序合并进一条可编译的主干；
- 全过程可追溯：谁、何时、基于什么基线、用什么模型、通过了什么。

### 3.2 不做什么（scope guard）

| 不做 | 原因 |
| --- | --- |
| 单文件小改动 | 建契约的成本大于改代码本身 |
| 强耦合的存量改造 | 热文件会把并行度压到 1（§10.4） |
| 架构设计决策 | 平台明确不做设计判断，`decisions[]` 必须由人给 |
| 替代人工 code review | 平台只保证「结构合法 + 验收通过」，不保证「设计正确」 |
| 需求管理 / 版本规划 / 发布 | 它只管一次需求到合并 |
| 通用 CI | 只跑与任务相关的构建与测试，不做流水线编排 |
| 公共 Agent 集市 | 私有工程场景，不做匿名撮合、信誉交易 |
| 激励、代币、结算 | 私有场景的痛点是分配不是激励；可交易的积分必然被刷（§10.5） |

### 3.3 三个成立前提

1. **有 ≥3 个可独立干活的执行体**（人 / 账号 / 机器）。只有 1 个，分布式的全部机制都是净开销。
2. **工作以新增文件、新增模块为主**。改造存量时，注册表、路由、清单这些热文件会把 DAG 串行化。
3. **接受「平台只保证结构与验收，不保证内容质量」**，并有评审带宽兜底。

### 3.4 回本门槛

| 指标 | 低于此值不建议上 | 说明 |
| --- | --- | --- |
| 独立执行体 | 3 | 2 个的收益抵不上协调成本 |
| 每周子任务数 | 15 | 更低时人工串行更快 |
| 单任务规模 | 100–400 行 | 太小则契约成本占比过高，太大则失败代价过高 |

### 3.5 与现有方案的关系

- **不是**任务队列（Airflow / Celery）：它们调度程序，不处理"谁的接口对不上"。
- **不是** Agent 编排框架（LangGraph / CrewAI）：它们由平台调用模型，风控与成本集中。
- **不是** A2A / Agent 集市：那是公共网络的任务撮合，没有代码级契约。
- **是**「私有工程 + 代码契约 + 终端主动拉取」的三元组合。单点都不新，组合是新的。
