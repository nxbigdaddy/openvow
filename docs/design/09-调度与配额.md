## 10.1 认领 SQL（写集互斥必须在这里）

```sql
WITH candidate AS (
  SELECT t.id
  FROM tasks t
  WHERE t.state = 'queued'
    AND t.kind = ANY($1)                      -- 终端声明的能力
    AND NOT EXISTS (                          -- 前驱未 accepted
      SELECT 1 FROM task_deps d JOIN tasks p ON p.id = d.parent_id
      WHERE d.child_id = t.id AND p.state <> 'accepted'
    )
    AND NOT EXISTS (                          -- 写集互斥
      SELECT 1 FROM tasks o
      WHERE o.state = 'claimed' AND o.lease_until > now()
        AND o.writes && t.writes
    )
    AND NOT EXISTS (                          -- 集成全局串行
      SELECT 1 FROM tasks g
      WHERE g.kind IN ('integration','repair') AND g.state = 'claimed'
        AND t.kind IN ('integration','repair')
    )
  ORDER BY
    CASE t.kind WHEN 'integration' THEN 2 WHEN 'repair' THEN 3 ELSE 1 END,
    t.priority DESC, t.created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE tasks
SET state = 'claimed', terminal_id = $2, lease_id = $3,
    lease_until = now() + make_interval(secs => $4)
FROM candidate
WHERE tasks.id = candidate.id
RETURNING tasks.*;
```

两个工程要点：

1. `writes` 必须是 `text[]` + GIN 索引，`&&` 才能用；`jsonb` 走不通。
2. 写集互斥是**同一条语句里的谓词**。规范说 A、示例写 B，实现时一定按示例写。

## 10.2 租约、心跳、检查点

| 机制 | 规格 |
| --- | --- |
| 租约 | 默认 1800s；返回 `lease_expires_at`（服务端时钟） |
| 心跳 | 每 300s；返回 `remaining_seconds`；`409` 时立即停手且不提交 |
| 过期 | `claimed → queued`，`attempts += 1`（上限 2）→ `needs_human` |
| 检查点 | `POST /v1/checkpoint`，最多保留 5 个 |
| 续跑 | 重试时 `claim` 返回 `resume`，终端可从半成品继续 |
| 幂等 | `submit` 按 `(task_id, attempt)` 幂等，重复提交返回首个结果 |

**检查点解决"90 分钟白干"**：租约只保证锁不死，不保证工作不丢。

## 10.3 信任分与抽检

```
trust = 近 20 次提交中「一次通过」的比例
```

| 条件 | 复跑比例 |
| --- | --- |
| 新终端（< 5 次） | 100% |
| trust ≥ 0.95 且 n ≥ 20 | 5% |
| trust ≥ 0.90 | 20% |
| 其它 | 50% |

复跑未通过不直接判死（可能是环境差异），而是降 trust 并要求人工复核。没有这个旋钮，你要么全量复跑（变成 CI 农场），要么完全信任（等于没验收）。

## 10.4 热文件策略

注册表、路由表、`mod.rs`、`package.json`、DI 容器——任何新模块都要动它们。三种策略按优先级：

1. **消除**：约定式自动发现（glob 扫描、entrypoint 目录），新增模块不需要改中心文件。**唯一真正的解法**。
2. **隔离**：设计 `registrar` 任务，写集只含中心文件，放在图末尾串行执行。
3. **追加合并**：允许标记区间

   ```rust
   // openvow:append:routes
   // openvow:end
   ```

   多个任务往各自区间追加，集成时按确定性顺序拼接。平台只拼接，不改内容。

三种都做不到，这个项目不适合 OpenVow。

## 10.5 贡献与配额（fair-share，不是奖励）

**这一节解决的是分配公平，不是激励。**

私有团队里会出现这种局面：A 挂了三台机器、三个账号，B 一台没挂但天天派活。半年后 A 会问"凭什么我出的算力给你跑需求"。这不是激励问题，是分配问题。

HPC 集群几十年前就遇到过同一件事，答案叫 **fair-share scheduling**（SLURM 的 priority multifactor）。它的核心不是发奖励，而是**记账 + 按历史用量调整优先级**。OpenVow 抄的是这个，不是积分商城。

### 三条边界

| 边界 | 含义 |
| --- | --- |
| 只记账，不结算 | 报表给人看，人对账；系统不碰钱。一旦碰钱就要有仲裁、发票、合规，成本会超过产品本身 |
| 只降权，不阻断 | 超配额只降低 claim 优先级，不硬拒绝。硬拒绝会让整张 DAG 卡死，比不公平更糟 |
| 只算 accepted | 贡献口径用 `accepted` 任务的终端时长，不用提交次数，否则又诱导刷量 |

### 数据

```sql
CREATE TABLE owners (
  id     text PRIMARY KEY,
  name   text NOT NULL,
  period text NOT NULL DEFAULT 'week'       -- week / project
);

CREATE TABLE usage_ledger (
  owner_id         text NOT NULL REFERENCES owners(id),
  period_key       text NOT NULL,           -- 如 2026-W43 或 proj-14
  terminal_seconds bigint NOT NULL DEFAULT 0, -- 贡献：终端实际执行时长
  accepted_tasks   int    NOT NULL DEFAULT 0,
  token_est        bigint NOT NULL DEFAULT 0, -- 终端自报，仅参考
  updated_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (owner_id, period_key)
);
```

### 优先级

```sql
-- claim 的 ORDER BY 多一项；fairshare_bonus 由离线任务每 5 分钟刷新
ORDER BY
  CASE t.kind WHEN 'integration' THEN 2 WHEN 'repair' THEN 3 ELSE 1 END,
  (t.priority + o.fairshare_bonus) DESC,
  t.created_at
```

建议算法（区间 0–30，不改变 kind 的先后）：

```
ratio = 该 owner 本周期消耗 / 该 owner 本周期贡献
bonus = round( 30 * (1 - min(ratio, 3) / 3) )
```

`ratio = 0` 时满额 +30；`ratio ≥ 3` 时为 0（不再加成，但不惩罚）。

### 明确不做

| 不做 | 原因 |
| --- | --- |
| 积分 / 代币 | 需要结算与信任背书，滑向 marketplace；可交易必然出现套利 |
| 竞价 / 拍卖 | 平台无法验证真实 token 消耗，成本必被虚报 |
| 排行榜 | 诱导抢简单任务、拆任务刷数量，直接污染调度与质量信号 |
| 给 Agent 做 reward shaping | 违反"平台不参与模型行为"的边界，且不可控 |

需要可见性时，用绝对值不用名次：「本需求由 5 个终端、3 位贡献者完成，A 提供 62% 的算力」。

### 什么时候才启用

三个条件满足任一：

1. 出现 ≥3 个独立所有者（按"谁掏钱、谁受益"算，不是终端数）；
2. 算力不对等且协商不动；
3. 跨项目抢同一批终端。

在此之前（M0–M2）不实现：单人场景下这层记账纯属负债。
