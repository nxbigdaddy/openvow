任务状态机

只有 accepted 解锁下游；merged 需要 L4 集成通过。状态以租约为唯一时钟。

异常出口： rejected L0–L3 失败，计入 attempts，可重试； lease_expired 终端失联 → 回到 queued； attempts > max → needs_human，不再自动派发； stale base_commit 落后且写集相交 → 要求 rebase 重提交。

校验分层：合规 ≠ 可用

1.0 只做到 L2，2.0 补上 L3 行为验收 —— 这是「零二次加工」唯一可验证的承诺。

L0结构路径规范化、写集越界、符号链接、大小上限
L1完整平台重算 sha256、required_files 齐全
L2形状JSON Schema、linter 零 error
L3行为 · acceptancebuild / test 退出码符合预期，终端跑 + 平台抽检
L4集成 · 全量测容器内 apply 到主干后整体构建

L0–L2 失败 ⇒ rejected；L3 通过 ⇒ accepted（解锁下游）；L4 通过 ⇒ merged。 只信执行证据，不信终端自报的 status: success。

拆解层 · 拆解本身也是一个任务

平台内置拆解模型 = 把风控重新集中回平台。正确形态是让一个自带强模型凭证的 planner 终端 去 claim 一个 meta 任务， 产出机器可校验的 task_graph.json：机器只保证结构合法，人只对图签字。

01合规 ≠ 可用

格式全对、里面全是 pass 的产物也能过 Schema。所以必须有 acceptance：写不出验收命令的任务，不许入库。

02写集不相交

两个任务都改同一个文件，各自 100% 合规，合并必然冲突。writes 相交 ⇒ 禁止并行，宁可少并行，不要假并行。

03租约即锁

无期限的锁在终端随时失联的环境里必然死锁。lease_until + 心跳 + 过期回收 + attempts 上限，一步都不能省。

04模型 Key 永不上平台

平台只持终端接入 token。两种凭证必须分开叙述——否则「不持有任何密钥」和「防投毒」会直接打架。
